# Ревью PB-03: SOC-аналитик L2 с опытом работы в SOC 5+ лет

Объект ревью: `/mnt/project-files/ir-study/drafts/PB-03-account-compromise.md` (PB-03 «Компрометация учётной записи»).
Контекст: учебный IR-план «Альфа-Трейд» (`/mnt/project-files/ir-study/source/ir-plan.md`): роли L1 / L2 / IM / ИТ / владелец системы / юрист-DPO / PR / директор, критичность P1–P4, полномочия L2 (изолировать одну рабочую станцию, заблокировать один внешний IP), 152-ФЗ, облачная почта и файлы с журналами входов и MFA.

Пометки в тексте:
- **[проверить]**: в сути уверен, но точное название, код, поле или срок надо сверить с документацией вашего продукта или первоисточником.
- **[допущение]**: в IR-плане этого нет, я предполагаю типичную картину для компании такого размера.
- **[псевдокод]**: запрос показывает логику, синтаксис и имена полей надо подогнать под вашу SIEM и нормализацию.

Важная оговорка про продукты. В IR-плане не названы ни SIEM, ни EDR, ни провайдер облачной почты. Для облака я привожу примеры на Microsoft 365 / Entra ID, потому что у них лучше всего документированы журналы и операции. Если у «Альфа-Трейд» российский провайдер (Яндекс 360, VK WorkSpace и т. п.), набор журналов и возможность принудительно отозвать сессии могут отличаться. Это надо выяснить на этапе подготовки, а не в 3 часа ночи **[проверить]**.

## 0. Итог в трёх строках

1. Каркас верный и содержит три вещи, которые новички обычно упускают: звонок пользователю по независимому каналу, сброс сессий и токенов вместе с паролем, проверка правил пересылки и новых устройств MFA. Это хорошая «память о главном».
2. Как рабочий документ для смены плейбук не годится. Нет критериев TP/FP, нет ветки «не дозвонились ночью», нет различия между доменной учёткой, облачной учёткой, VPN и сервисной учёткой, нет ни одного запроса к SIEM, нет порядка «сначала сохранить, потом удалять», нет полномочий на отключение учётки.
3. Модель угроз отстаёт на 3–4 года: сценарий описан как «украли пароль», а в 2025–2026 основные векторы это кража сессии (AiTM-фишинг, стилеры), MFA fatigue, злоупотребление OAuth и социальная инженерия на сервис-деск. Против них «сменить пароль и включить MFA» не работает.

## 1. Релевантность (практика SOC/IR 2025–2026)

### 1.1. Что соответствует практике

| Что в плейбуке | Почему это правильно |
| --- | --- |
| Звонок пользователю по телефону, не по почте | Если почта скомпрометирована, атакующий прочитает вопрос и ответит сам. Внеполосная проверка (out-of-band) это стандарт. |
| «Только смена пароля не выкидывает уже вошедшего атакующего» | Ключевая мысль. Refresh-токены облака, cookie сессии, VPN-сессия и билеты Kerberos переживают смену пароля. |
| Удалить чужие устройства MFA и правила пересылки | Это два самых частых способа закрепления в почтовой учётке. |
| Проверить хост сотрудника в EDR | Без этого не закрыть сценарий «пароль украл стилер»: атакующий получит и новый пароль. |
| Переход в PB-05 при доступе к ПД | Связь с 152-ФЗ нужна, без неё 24-часовой срок уведомления РКН пропускают. |
| T1078 Valid Accounts | Основная техника сценария указана верно. |
| «Типичная ошибка» в конце | Полезный формат, его стоит расширить до списка из 5–7 пунктов. |

### 1.2. Что устарело, неточно или неверно

**1. Модель «украли пароль» вместо «украли сессию».** Раздел «Устранение» перечисляет «фишинг, вредонос-стилер, утечка с другого сайта» как способы украсть *пароль*. В 2025–2026 значительная доля компрометаций облачных учёток идёт через:
- **AiTM-фишинг** (reverse-proxy фишинг-киты, публично описаны Evilginx, EvilProxy, Tycoon 2FA и подобные): пользователь вводит пароль и проходит MFA на прокси-странице, атакующий забирает cookie сессии. MFA не спасает, пароль атакующему уже не нужен.
- **Стилеры** (семейства уровня Lumma, RedLine, Vidar и их наследники; конкретные «лидеры года» меняются **[проверить]**): уносят не только пароли из браузера, но и cookie, и токены. Вход по украденной cookie часто вообще не создаёт события «вход с паролем».
- **MFA fatigue / push bombing** (ATT&CK T1621 Multi-Factor Authentication Request Generation): пароль у атакующего уже есть, он шлёт push, пока пользователь не нажмёт «Подтвердить».
- **Device code phishing и OAuth consent phishing**: пользователя заставляют ввести код на легитимной странице провайдера или дать права вредоносному приложению. Пароль не меняется, MFA пройден, доступ у атакующего через токен приложения (T1528 Steal Application Access Token). Кампании с device code phishing против M365 широко описывались в 2025 году **[проверить детали]**.
- **Социальная инженерия на сервис-деск**: атакующий звонит в ИТ от имени сотрудника и просит сбросить пароль или MFA. Это напрямую касается «Альфа-Трейд», потому что именно ИТ в плейбуке сбрасывает пароли.

Последствие: блоки «Триггеры», «Сдерживание» и «Устранение» нужно переписать с учётом того, что у атакующего может быть **сессия без пароля** и **легитимно пройденный MFA**.

**2. Список техник ATT&CK слишком короткий.** Для такого плейбука ожидаю минимум:

| Техника | Зачем в плейбуке |
| --- | --- |
| T1078.002 Domain Accounts, T1078.004 Cloud Accounts | Разные журналы и разные действия сдерживания |
| T1110.001 / .003 / .004 (подбор, password spraying, credential stuffing) | Разные паттерны в SIEM и разная реакция |
| T1621 MFA Request Generation | MFA fatigue |
| T1539 Steal Web Session Cookie, T1550.004 Web Session Cookie | Кража и повторное использование сессии |
| T1557 Adversary-in-the-Middle | AiTM-фишинг **[проверить: точный номер подтехники для AiTM-фишинга]** |
| T1528 Steal Application Access Token | OAuth consent / device code |
| T1098.005 Device Registration | Регистрация своего устройства MFA / устройства в каталоге |
| T1114.003 Email Forwarding Rule | Правила пересылки |
| T1564.008 Email Hiding Rules | Правила, которые прячут письма (в «RSS», «Архив», удаление) |
| T1534 Internal Spearphishing | Рассылка из взломанного ящика коллегам |
| T1555.003 Credentials from Web Browsers | Стилер на хосте пользователя |

**3. «Невозможное путешествие» как триггер без оговорок.** Пример «Москва и Амстердам с разницей 10 минут» на практике чаще всего ложный: корпоративный или личный VPN, мобильный оператор с выходом через другой город, облачный прокси браузера, iCloud Private Relay, IPv6 у оператора. Одновременно настоящие атакующие всё чаще ходят через **резидентные прокси в стране жертвы**, и гео-правило их не видит. Правильная формулировка: гео — слабый сигнал, его надо обогащать (ASN хостинга, известность устройства, user-agent, тип клиента, был ли MFA, что делали после входа).

**4. «Заблокировать IP атакующего на NGFW и VPN».** Для облачной почты NGFW «Альфа-Трейд» вообще не стоит на пути: атакующий ходит к облаку напрямую из интернета. Блокировка на NGFW защитит только VPN и опубликованные сервисы. Кроме того:
- атакующие меняют IP за минуты (прокси-сети, облака);
- IP может быть CGNAT мобильного оператора, и вы заблокируете тысячи легитимных клиентов интернет-магазина, если правило применится и к сайту;
- блокировка до отзыва сессий предупреждает атакующего.
Блокировать IP имеет смысл в **политике условного доступа облака / IdP** и на VPN-шлюзе, и только как дополнение к отзыву сессий.

**5. Критичность «P1, если администратор домена» слишком узкая.** По самому IR-плану P1 это «утечка ПД, затронут AD». Значит P1 также:
- любая учётка с правами в AD (Account Operators, Server Operators, Backup Operators, делегированные права на OU, права на GPO), не только Domain Admins;
- администратор облачного тенанта, EDR, SIEM, NGFW, системы резервного копирования, гипервизора;
- учётка с доступом к базе клиентов, админке сайта или платёжным настройкам, если есть признаки доступа к данным;
- массовая компрометация (несколько учёток одной кампанией).
Отдельно стоит выделить **финансы и руководство** (риск BEC, подмена реквизитов): технически это P2, но с обязательным подключением финансового директора.

**6. Только 4624 / 4625 в артефактах.** Для расследования компрометации доменной учётки этого мало: нужны Kerberos (4768, 4769, 4771), NTLM (4776), блокировки (4740), смены паролей (4723, 4724), изменения групп (4728, 4732, 4756), RDP (4778/4779 и журналы TerminalServices). Таблица в разделе 3.3.

**7. «Включить MFA, если его не было».** В 2026 это минимально необходимое, но недостаточное действие. Push без number matching уязвим к fatigue, SMS к SIM-swap, любой «обычный» MFA к AiTM. Рекомендация уровня плейбука: для привилегированных учёток phishing-resistant MFA (FIDO2-ключи / passkeys), для всех push с number matching и запрет устаревших протоколов (IMAP/POP/SMTP AUTH без MFA, пароли приложений). И главное: **регистрация нового метода MFA после инцидента только с проверкой личности**, иначе атакующий зарегистрирует свой первым.

**8. Пропущена роль сервис-деска как вектора и как исполнителя.** ИТ сбрасывает пароль, но плейбук не говорит, как ИТ убеждается, что звонит настоящий сотрудник, и куда передаётся временный пароль (не на почту).

**9. Сценарий «пользователь сам подтвердил push».** Триаж строится на вопросе «это был он?». При MFA fatigue и AiTM пользователь честно скажет «да, я подтвердил / да, я входил», потому что действительно нажимал. Вопрос надо задавать иначе (скрипт в разделе 5.4).

## 2. Полнота: что пропущено

Ниже перечислено всё, что должно быть в полноценном плейбуке такого типа. Жирным отмечено то, без чего по плейбуку нельзя работать на смене.

### 2.1. Шапка и границы

- Идентификатор, версия, дата, владелец плейбука, дата следующего пересмотра.
- **Область действия:** какие учётки покрывает (доменные AD, облачные почта/файлы, VPN, 1С, админка сайта, учётки клиентов магазина или нет).
- **Границы с соседними плейбуками.** Я читал только PB-03, поэтому формулирую условно: если PB-10 «Компрометация облачной учётки» существует, надо явно развести, где кончается PB-03 и начинается PB-10, иначе на смене будут читать оба и делать разное. Варианты: PB-03 это общий плейбук по идентичности, PB-10 его облачное приложение; или PB-03 только AD/VPN/внутренние системы. Также нужны ссылки на PB-01 (фишинг как источник), PB-04 (вредонос на хосте пользователя), PB-05 (утечка ПД), PB-07 (инсайдер: «это был он, но он злоупотребляет»), PB-S4 (сработка EDR).
- **Учётки клиентов интернет-магазина** (credential stuffing на личные кабинеты) это отдельный сценарий с другими данными и другими действиями. Надо явно сказать, что PB-03 его не покрывает, или добавить ветку.
- Список ATT&CK (раздел 1.2, п. 2).

### 2.2. Подготовка (специфика сценария)

- **Журналы:** политика аудита на DC включает Logon, Kerberos Authentication Service, Kerberos Service Ticket Operations, Credential Validation, Account Lockout, User/Security Group Management **[проверить по вашей GPO]**. Без этого 4768/4771/4776/4740 в SIEM просто не будет.
- **Облако:** включён журнал аудита почты (операции над правилами, пересылкой, правами на ящик, отправкой), журналы входов выгружаются в SIEM. Узнать срок хранения журналов у провайдера: у облачных провайдеров он бывает 7–30 дней в зависимости от лицензии **[проверить у своего провайдера]**. Если в SIEM не выгружается, первым действием инцидента должен быть экспорт.
- **Возможности сдерживания у провайдера:** можно ли принудительно завершить все сессии и отозвать токены, удалить метод MFA, отозвать согласие OAuth-приложения, запретить IMAP/POP. Если чего-то нельзя, это записывается как риск в плейбук.
- **Справочник контактов сотрудников** из HR-системы (не из AD, где атакующий с правами мог поменять поле `mobile` / `telephoneNumber`). Для руководства и ИТ-администраторов резервный номер.
- **Список привилегированных и сервисных учёток** с владельцами: какие можно отключать без согласования, какие ломают бизнес (интеграция 1С, сайт, бэкап).
- **Базовая линия:** обычные страны, ASN, устройства и время работы для групп пользователей; список корпоративных egress-IP и IP VPN, чтобы они не давали FP.
- **Процедура сброса пароля и MFA сервис-деском** с проверкой личности (обратный звонок на номер из HR, подтверждение руководителем, личная явка для администраторов).
- **Временный пароль / временный код доступа** передаётся по телефону или лично, не по почте.
- Предварительно согласованные полномочия L2 на действия с учётками (раздел 2.4).

### 2.3. Триггеры и источники

В плейбуке четыре триггера без источника. Не хватает:

| Триггер | Источник |
| --- | --- |
| Password spraying: один IP, много учёток, мало попыток на каждую | DC (4625/4771/4776), облачные входы, VPN |
| Подбор на одну учётку, блокировка 4740 | DC, VPN |
| Успешный вход после серии неудачных | DC, облако, VPN |
| Вход с ASN хостинга / VPN-сервиса / Tor | Облако, VPN + TI-обогащение |
| Вход с нового устройства / нового user-agent / устаревшего протокола (IMAP, POP, ActiveSync, SMTP AUTH) | Облако |
| Регистрация нового метода MFA, особенно вскоре после входа с нового IP | Журнал аудита IdP |
| Регистрация устройства в каталоге | Журнал аудита IdP |
| Согласие (consent) на OAuth-приложение с правами на почту/файлы | Журнал аудита IdP |
| Создание правила в ящике (пересылка, перемещение, удаление), изменение пересылки на уровне ящика, выдача прав на ящик | Журнал аудита почты |
| Массовая отправка писем изнутри, внутренний фишинг | Почтовый шлюз, аудит почты |
| Массовое скачивание файлов из облачного хранилища | Аудит файлов |
| Смена пароля или MFA через сервис-деск, о которой пользователь не знает | Тикет-система, 4724 |
| Добавление учётки в привилегированную группу | DC (4728/4732/4756) |
| Одновременные VPN-сессии одного пользователя с разных IP | VPN |
| Стилер / ClickFix / подозрительный доступ к хранилищу паролей браузера на хосте | EDR, антивирус |
| Учётка найдена в утечке или в логах стилеров | TI-подписка, внешнее уведомление **[допущение: есть ли такая подписка]** |
| Жалоба пользователя («пришли запросы MFA», «коллеги получили от меня странное письмо») | Звонок / тикет |
| Внешнее уведомление (контрагент получил письмо с изменёнными реквизитами) | Звонок / почта |

### 2.4. Роли, RACI и полномочия

IR-план даёт L2 право изолировать одну станцию и заблокировать один IP, но **ничего не говорит про учётки**. В результате в 3 часа ночи L2 не знает, может ли он сам отключить учётку бухгалтера, и будет будить IM. Нужно:

| Действие | Кто делает | Чьё согласие |
| --- | --- | --- |
| Отозвать сессии и токены обычного пользователя | L2 (или ИТ по заявке L2) | Не нужно при подтверждённом TP |
| Отключить обычную учётку | L2 / ИТ | Не нужно при подтверждённом TP; уведомить IM в течение часа |
| Отключить учётку руководителя (VIP) | ИТ | IM; IM информирует директора |
| Отключить привилегированную учётку | ИТ | IM |
| Отключить сервисную учётку | ИТ | IM + владелец системы (может остановить бизнес-процесс) |
| Массовые действия (>5 учёток, глобальный сброс сессий, запрет протокола для всех) | ИТ | IM; при влиянии на продажи — владелец системы |
| Блокировка IP/ASN в условном доступе облака | L2 / ИТ | Не нужно для одного IP; для страны или ASN — IM |
| Разговор с пользователем о деталях | L1 (первичный), L2 (детальный) | — |
| Решение «был ли доступ к ПД» | L2 даёт факты, DPO решает | IM |
| Контакт с банком / контрагентами при BEC | Финансы + юрист | IM |

Число «5 учёток» условное **[допущение]**.

### 2.5. Триаж: решения, которых нет

- **Критерии TP/FP** (раздел 3.2).
- **Ветка «не дозвонились»** (ночь, отпуск, больничный). Сейчас триаж упирается в звонок и останавливается.
- **Ветка «пользователь говорит, что это он»**: что проверить, прежде чем поверить (устройство, user-agent, MFA-метод, что делалось после входа).
- **Ветка «пользователь подтвердил push, но не входил»**: это TP, а не «пользователь сам виноват, закрываем».
- **Неудачный подбор без успешного входа**: P4, но надо проверить, что ни одна учётка из списка не вошла успешно с того же IP (spraying обычно «попадает» в 1–2 из сотни).
- **Классификация учётки**: обычная / VIP / финансы / привилегированная / сервисная / общая (shared) / внешний подрядчик. От этого зависит критичность и порядок.
- **Решение о критичности с пересмотром**: исходная P3 «подозрительный вход», повышение до P2 при подтверждении, до P1 при привилегиях, ПД или массовости.

### 2.6. Расследование L2: что не перечислено

Строка «что делали после входа» в одном пункте — это на самом деле 80% работы. Нужно расписать:

1. **Окно компрометации:** первое подозрительное событие (не первая сработка!) и последнее. Искать назад минимум 30 дней или на всю глубину журналов.
2. **Как вошли:** пароль + MFA, пароль без MFA (устаревший протокол), cookie без пароля, токен приложения, сброс через сервис-деск.
3. **Инфраструктура атакующего:** все IP, ASN, user-agent, ID устройств, ID сессий.
4. **Пивот по инфраструктуре:** кто ещё входил с этих IP / ASN / user-agent. Это поиск других жертв, и его почти всегда забывают.
5. **Пивот по источнику:** если пришло фишинговое письмо, кто ещё его получил и кто кликнул (PB-01).
6. **Почта:** правила в ящике (включая скрытые), пересылка на уровне ящика, делегирование и права (FullAccess, SendAs, SendOnBehalf), подписи, что читали, что искали, **что отправили** (внутрь и наружу), что удалили (атакующие удаляют отправленные письма и ответы).
7. **Файлы:** скачивания, массовый доступ, внешние ссылки на общий доступ, синхронизация на новое устройство.
8. **IdP:** новые методы MFA, изменение телефона/почты для восстановления, зарегистрированные устройства, согласия OAuth, пароли приложений.
9. **AD и внутренние системы:** входы на хосты (с каких, тип входа), RDP, VPN-сессии, изменения групп, доступ к файловому серверу, 1С, базе клиентов, админке сайта.
10. **Хост пользователя:** признаки стилера или удалённого доступа (раздел 3.7).
11. **Blast radius:** к чему у учётки вообще есть доступ (группы, приложения, данные). Это ответ на вопрос юристу «мог ли он видеть ПД».
12. **Повторное использование пароля:** этот же пароль мог использоваться в 1С, админке сайта, на личных сервисах, в SSH-ключах и API-токенах в коде.

### 2.7. Сдерживание: что пропущено

- **Порядок действий** (сохранить → отозвать сессии → отключить/сбросить → удалить закрепление → блокировать инфраструктуру). Сейчас блокировка IP идёт последней, а удаление правил вторым, то есть до их экспорта.
- **Одновременность:** при подозрении на подготовленного атакующего все действия выполняются одним пакетом за несколько минут, иначе после первого шага он заметит и закрепится иначе.
- **Kerberos:** билеты, выданные до смены пароля, живут до истечения (по умолчанию TGT 10 часов). Отключение учётки надёжнее, плюс завершение сессий на хостах **[проверить детали поведения KDC для отключённых учёток в вашей версии AD]**.
- **Облачные токены:** после отзыва refresh-токенов уже выданный access-токен может работать до своего истечения (порядка часа) у приложений без механизма непрерывной оценки доступа **[проверить для вашего провайдера]**. Значит мониторинг 1–2 часа после отзыва обязателен.
- **VPN:** активную сессию нужно завершить на шлюзе, смена пароля её не рвёт. Если VPN по сертификату, отозвать сертификат.
- **Устаревшие протоколы и пароли приложений:** IMAP/POP/ActiveSync-партнёрства и пароли приложений обходят MFA и могут переживать смену пароля **[проверить для провайдера]**.
- **OAuth-приложения:** отозвать согласие, иначе доступ остаётся без пароля.
- **Устройства:** удалить зарегистрированные атакующим устройства (MFA и каталог).
- **Данные для восстановления пароля:** телефон и почта для самостоятельного сброса, если атакующий их поменял.
- **Сдерживание на хосте:** если стилер на хосте пользователя — изоляция хоста в EDR **до** выдачи нового пароля.
- **Рассылка из ящика:** если атакующий отправил фишинг коллегам или контрагентам, удалить эти письма из ящиков получателей (возможность зависит от почты) и предупредить контрагентов.

### 2.8. Артефакты: что пропущено

- Приоритет сбора (что исчезнет первым: облачные журналы по сроку хранения, активные сессии, содержимое правил до удаления).
- Экспорт правил и настроек ящика **до** их удаления.
- Экспорт журналов входов и аудита за всё окно компрометации, хеш файлов экспорта, место хранения (цепочка хранения, chain of custody).
- Сохранение отправленных и удалённых писем (удержание ящика / восстанавливаемые элементы).
- Атрибуты учётки AD (`pwdLastSet`, `whenChanged`, `lastLogonTimestamp`, членство в группах, метаданные репликации).
- Артефакты хоста пользователя (если стилер — триаж-коллекция EDR или образ).
- Журнал VPN, NGFW, прокси за окно.
- Скриншоты и объяснение сотрудника (кратко, в тикете, со временем).
- Список IOC: IP, ASN, user-agent, домены фишинга, ID приложения OAuth, ID устройств.

### 2.9. Ветвления (сценарии), которых нет

| Ветка | Почему отдельная |
| --- | --- |
| Привилегированная учётка AD | P1, риск полной компрометации домена, другой порядок (поиск закрепления в AD) |
| Сервисная учётка | Звонить некому, отключение ломает бизнес, пароль зашит в конфиги |
| Облачный администратор | Атакующий может удалить журналы, создать свои учётки и приложения |
| BEC / финансы | Счёт идёт на часы: банк может успеть отозвать платёж |
| MFA fatigue | Пароль у атакующего уже есть: смена пароля обязательна, даже если вход не удался |
| Стилер на хосте | Сначала хост, потом пароль; сбросить все пароли, которые были в браузере |
| AiTM / кража cookie | Пароль сменить, но главное отозвать сессии; искать письмо-источник и других кликнувших |
| Массовый spraying без успеха | P4, но с поиском «единичного успеха» |
| Массовый spraying с успехом | P2/P1, несколько учёток, координированное сдерживание |
| Пользователь недоступен | Решение по силе сигнала (раздел 5.5) |
| Инсайдер («это был он») | Переход в PB-07, не предупреждать сотрудника, подключить HR и юриста |
| Внешний подрядчик | Звонить через ответственного за договор; доступ подрядчика можно отключить быстрее |
| Учётки клиентов магазина | Отдельный сценарий (credential stuffing на личные кабинеты) |

### 2.10. Коммуникации

- Что говорить пользователю (и чего не говорить: детали расследования, IOC).
- Кто сообщает руководителю пользователя и HR (при инсайдере — только IM).
- Предупреждение коллег, если из ящика рассылался фишинг: кто и каким текстом.
- Контрагенты при BEC: только по телефону из договора, не отвечая на письмо.
- Финансы и банк при подмене реквизитов.
- Юрист/DPO: какие факты передаются и в какой момент запускается 24-часовой отсчёт по 152-ФЗ (по IR-плану — с момента выявления).
- Ритм статусов IM (по IR-плану P1 каждые 2 часа, P2 дважды в день).
- Резервный канал, если скомпрометирована почта администратора или руководителя.

### 2.11. Устранение и восстановление

- Найти корневую причину и **доказать** её артефактом, а не предположением.
- Если стилер: переустановка или подтверждённая очистка хоста, смена всех паролей, сохранённых в браузере, отзыв всех сессий во всех сервисах, включая личные (рекомендация сотруднику).
- Ротация секретов, к которым был доступ: API-ключи, SSH-ключи, пароли сервисных учёток, известные пользователю.
- Поиск закрепления: новые учётки, приложения, правила, делегирования, GPO (для привилегированных).
- Повторная регистрация MFA с проверкой личности.
- Возврат доступа: кто подтверждает, что учётку можно включить.
- Усиленное наблюдение: какие правила SIEM, на какой срок, кто смотрит.
- Обучение пользователя без поиска виновных.

### 2.12. Закрытие, уроки, метрики

- Проверяемые критерии закрытия (раздел 5.12). «Все его действия изучены» не проверяется.
- Метрики сценария: время от первого подозрительного входа до сработки, от сработки до отзыва сессий, сколько учёток затронуто, сколько писем отправлено атакующим.
- Обновление детекта: какое правило должно было сработать раньше.

## 3. Детализация: где слишком общо и что расписать

### 3.1. Хронометраж (что делать в первые 60 минут)

Цифры учебные, согласованы с таблицей критичности IR-плана **[допущение]**.

| Время от сработки | Кто | Что |
| --- | --- | --- |
| 0–15 мин | L1 | Принять сработку, завести тикет, обогатить (кто пользователь, класс учётки, IP/ASN/страна, устройство, был ли MFA), проверить по критериям 3.2 |
| до 15 мин | L1 | Если учётка привилегированная или есть «сильный сигнал» — сразу эскалация L2 (и IM для P1), не дожидаясь звонка |
| 15–30 мин | L1 | Звонок пользователю по номеру из HR-справочника, по скрипту 5.4. Две попытки с интервалом 5 минут |
| 15–45 мин | L2 | Решение TP/FP, экспорт облачных журналов и правил ящика, определение окна и инфраструктуры |
| до 60 мин после подтверждения | L2 / ИТ | Отзыв сессий, отключение или сброс, удаление закрепления (порядок 5.6) |
| 1–4 ч | L2 | Пивот по инфраструктуре, поиск других жертв, оценка доступа к ПД, передача фактов DPO |
| до 24 ч от выявления | DPO / IM | Решение по уведомлению РКН (если затронуты ПД) |

### 3.2. Критерии TP/FP для L1

**Сильные сигналы** (любой один = эскалация L2 сразу, по умолчанию TP до опровержения):
- новый метод MFA или новое устройство зарегистрированы вскоре после входа с нового IP;
- правило в ящике с пересылкой наружу, удалением или перемещением писем в редко используемые папки (RSS, Архив, Заметки), имя правила из одного-двух символов («.», «..»);
- согласие на OAuth-приложение с правами на почту/файлы, которое не из списка разрешённых;
- вход с ASN хостинга/VPN-сервиса/Tor и затем действия в почте или файлах;
- пользователь сообщает о запросах MFA, которых не делал, или о том, что «подтвердил случайно»;
- внутренняя рассылка из ящика пользователя со ссылкой/вложением, на которую жалуются получатели;
- успешный вход после серии неудачных с одного внешнего IP;
- одновременно активные сессии из двух разных стран на разных устройствах;
- учётка добавлена в привилегированную группу вне заявки.

**Слабые сигналы** (по одному — не повод отключать учётку, но повод проверять):
- новая страна без других аномалий;
- «невозможное путешествие» между корпоративным egress и мобильной сетью;
- новый браузер на известном устройстве;
- единичные неудачные входы.

**Признаки FP** (фиксировать, чем подтверждено):
- IP входит в список корпоративных egress / VPN / известных прокси;
- устройство управляемое и известное (ID совпадает с прошлыми входами), user-agent обычный;
- пользователь подтвердил командировку, и это подтверждено вторым источником (руководитель, заявка на командировку, бронирование) **[допущение: такой источник есть]**;
- после входа нет действий из списка «сильных сигналов».

Важно: «пользователь сказал, что это он» само по себе не FP при наличии сильного сигнала.

### 3.4. VPN, NGFW, прокси

VPN-продукт в плане не указан, поэтому поля общие **[проверить для вашего шлюза]**:
- пользователь, внешний IP клиента, выданный внутренний IP, время начала и конца, длительность, объём трафика, версия клиента, имя хоста клиента, результат проверки устройства (posture), метод аутентификации, сертификат;
- что искать: одновременные сессии одного пользователя с разных внешних IP; новая версия или ОС клиента; вход в нерабочее время с последующим большим объёмом трафика; выданный внутренний IP атакующего — по нему дальше ищется всё во внутренней сети (NGFW, DC 4624 с этим `IpAddress`, EDR).

NGFW: по внутреннему IP VPN-сессии атакующего — к каким внутренним адресам и портам он ходил (445, 3389, 5985/5986, 1С, СУБД).

### 3.5. Облачная почта и IdP

На примере Microsoft 365 / Entra ID; у других провайдеров названия свои **[проверить]**.

**Журнал входов, поля:** `UserPrincipalName`, `IPAddress`, `Location` (страна/город), `AutonomousSystemNumber`, `UserAgent`, `ClientAppUsed` (браузер, мобильное приложение, IMAP, POP, SMTP, Exchange ActiveSync, «другие клиенты»), `AppDisplayName`, `ResourceDisplayName`, `DeviceDetail` (ID, ОС, управляемое/соответствующее), `AuthenticationRequirement` (однофакторная / многофакторная), `AuthenticationDetails` (каким методом прошёл MFA), `ConditionalAccessStatus`, `ResultType` (код ошибки), `IsInteractive`, `SessionId` / `CorrelationId`, уровень риска, если есть.

Полезные признаки:
- `ClientAppUsed` = устаревший протокол при включённом MFA → обход MFA;
- `UserAgent` вида скриптовых библиотек (python-requests, axios и т. п.) или отметка устаревшей аутентификации (в M365 встречается `BAV2ROPC`) **[проверить]**;
- вход с MFA «удовлетворено требованием в токене» с нового IP/устройства → возможное повторное использование токена/cookie **[проверить формулировку в вашем журнале]**;
- код ошибки 50126 (неверное имя или пароль) массово по многим учёткам → spraying; 500121 (неуспешная строгая аутентификация, в том числе отклонённый push) многократно по одной учётке → MFA fatigue **[проверить коды]**.

**Журнал аудита IdP, операции** (имена по Entra ID **[проверить]**): регистрация метода безопасности пользователем, изменение метода по умолчанию, регистрация устройства, согласие на приложение (`Consent to application`), добавление прав приложению, сброс/смена пароля, изменение телефона/почты для восстановления.

**Журнал аудита почты, операции** (имена по Exchange Online **[проверить]**): `New-InboxRule`, `Set-InboxRule`, `UpdateInboxRules` (правило, созданное из клиента Outlook), `Set-Mailbox` (параметры `ForwardingSmtpAddress`, `ForwardingAddress`, `DeliverToMailboxAndForward`), `Add-MailboxPermission`, `Add-RecipientPermission`, `Send`, `SendAs`, `SendOnBehalf`, `SoftDelete`, `HardDelete`, `MoveToDeletedItems`, `MailItemsAccessed` (что читали; доступность зависит от лицензии), а для файлов `FileDownloaded`, `FileAccessed`, `AnonymousLinkCreated`, `SharingSet`.

Если провайдер не даёт аналог `MailItemsAccessed` (что именно читал атакующий), то ответ на вопрос «был ли доступ к ПД в почте» будет «не можем исключить», и это надо так и записать для DPO.

### 3.6. Примеры запросов к SIEM

Имена полей нормализованные (`user`, `src_ip`, `outcome`, `src_asn`, `country`, `event_id` и т. п.). Синтаксис **[псевдокод]** в стиле SPL; ниже один пример в KQL.

**Q1. Password spraying: один IP, много учёток, мало попыток.**
```
index=auth (event_id IN (4625,4771,4776) OR source=cloud_signin outcome=failure) earliest=-1h
| stats dc(user) AS users, count AS attempts, values(user) AS user_list BY src_ip
| where users >= 10 AND attempts/users <= 3
| sort - users
```
Решение: если среди `user_list` есть успешный вход с того же `src_ip` (Q3) — это уже не P4.

**Q2. Подбор по одной учётке с разных IP.**
```
index=auth outcome=failure earliest=-1h
| stats count AS attempts, dc(src_ip) AS ips, values(src_ip) BY user
| where attempts >= 20
```

**Q3. Успешный вход после серии неудачных.**
```
index=auth earliest=-24h user=<USER> OR src_ip=<IP>
| sort 0 _time
| streamstats count(eval(outcome="failure")) AS fails_before BY user, src_ip reset_after="outcome=\"success\""
| where outcome="success" AND fails_before >= 5
```

**Q4. Новая страна / ASN для пользователя относительно 30-дневной базы.**
```
index=auth outcome=success user=<USER> earliest=-31d
| eval period=if(_time >= relative_time(now(),"-1d"),"new","baseline")
| stats values(period) AS periods, min(_time) AS first_seen BY user, country, src_asn
| where mvcount(periods)=1 AND periods="new"
```

**Q5. Всё, что делал IP атакующего, во всех источниках.**
```
(index=* src_ip=<ATTACKER_IP>) OR (index=* dest_ip=<ATTACKER_IP>) earliest=-30d
| stats count, values(user), values(action), min(_time), max(_time) BY sourcetype
```

**Q6. Кто ещё входил с инфраструктуры атакующего (поиск других жертв).**
```
index=auth outcome=success earliest=-30d (src_ip IN (<IP1>,<IP2>) OR src_asn=<ASN> OR user_agent="<UA>")
| stats min(_time) AS first, max(_time) AS last, values(src_ip) BY user
```
Осторожно с ASN: если это крупный облачный провайдер, будет много FP; сузить по user-agent и времени.

**Q7. Охота на правила в ящиках по всей компании за 30 дней.**
```
index=cloud_mail_audit earliest=-30d operation IN ("New-InboxRule","Set-InboxRule","UpdateInboxRules","Set-Mailbox")
| search parameters="*Forward*" OR parameters="*Redirect*" OR parameters="*DeleteMessage*" OR parameters="*MoveToFolder*"
| table _time, user, src_ip, operation, rule_name, parameters
```

**Q8. Новый метод MFA, зарегистрированный в течение 2 часов после входа с нового IP.**
```
index=idp_audit operation="User registered security info" earliest=-7d
| join type=inner user [ search index=auth outcome=success earliest=-7d | stats latest(_time) AS login_time, latest(src_ip) AS login_ip BY user ]
| where _time - login_time BETWEEN 0 AND 7200
```

**Q9. Внутренняя рассылка из взломанного ящика в окне компрометации.**
```
index=mail_gateway sender=<USER_EMAIL> earliest=<T_START> latest=<T_END>
| stats count, dc(recipient) AS rcpt, values(subject), values(url), values(attachment_name) BY direction
```
Если `rcpt` большой или есть ссылки/вложения — пивот: кто из получателей кликнул (PB-01).

**Q10. Изменения групп и паролей вокруг учётки.**
```
index=ad event_id IN (4723,4724,4738,4728,4732,4756,4720,4722,4767) (TargetUserName=<USER> OR SubjectUserName=<USER> OR MemberName="*<USER>*") earliest=-30d
| table _time, event_id, SubjectUserName, TargetUserName, MemberName, host
```

**Q11. Одновременные VPN-сессии пользователя с разных IP.**
```
index=vpn action=session_start earliest=-7d user=<USER>
| bin _time span=1h
| stats dc(src_ip) AS ips, values(src_ip), values(country) BY user, _time
| where ips > 1
```

**Q12. Пример KQL для Microsoft Sentinel / Entra SigninLogs [проверить имена полей в вашей версии].**
```kusto
SigninLogs
| where TimeGenerated > ago(30d)
| where UserPrincipalName =~ "<user@domain>"
| project TimeGenerated, IPAddress, AutonomousSystemNumber, Location = tostring(LocationDetails.countryOrRegion),
          AppDisplayName, ClientAppUsed, UserAgent, ResultType, AuthenticationRequirement,
          ConditionalAccessStatus, DeviceId = tostring(DeviceDetail.deviceId), IsInteractive, CorrelationId
| order by TimeGenerated asc
```

### 3.7. EDR: что смотреть на хосте пользователя

- **Стилер:** процесс, не являющийся браузером, читает хранилища браузеров: Chromium-браузеры — `...\User Data\<Profile>\Login Data`, `...\Network\Cookies`, `...\Local State`; Firefox — `logins.json`, `key4.db`, `cookies.sqlite`. Также папка `tdata` Telegram, кошельки, архив во `%TEMP%` и отправка POST на свежий домен или в API мессенджера.
- **ClickFix / фейковая капча:** запуск `powershell`/`mshta`/`cmd` из `explorer.exe` вскоре после посещения сайта; след в реестре `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\RunMRU`.
- **Происхождение:** файлы в `Downloads`, `%APPDATA%`, `%LOCALAPPDATA%\Temp`, «кряки» и «активаторы», установщики с файлообменников.
- **Удалённый доступ:** AnyDesk, TeamViewer, RustDesk и т. п. без заявки.
- **Закрепление:** задачи планировщика, ключи `Run`, службы, расширения браузера (вредоносные расширения тоже крадут сессии).
- **Сеть:** соединения хоста с IP/доменами, которые затем фигурируют во входах атакующего.
- Если найдено — переход в PB-04 / PB-S4, хост изолировать **до** выдачи нового пароля.

### 3.8. Команды для L2 / ИТ

Выполнять с доверенного административного хоста, каждое действие фиксировать в тикете со временем. PowerShell-модуль ActiveDirectory.

```powershell
# Сведения об учётке (до изменений, сохранить вывод в тикет)
Get-ADUser <user> -Properties * | Select-Object SamAccountName,Enabled,LockedOut,pwdLastSet,PasswordLastSet,lastLogonTimestamp,whenChanged,badPwdCount,MemberOf,mobile,telephoneNumber
Get-ADPrincipalGroupMembership <user> | Select-Object Name

# История изменений атрибутов (метаданные репликации) — кто и когда менял
repadmin /showobjmeta <DC> "<DistinguishedName пользователя>"

# Отключение и сброс пароля (после экспорта и решения в тикете)
Disable-ADAccount -Identity <user>
Set-ADAccountPassword -Identity <user> -Reset -NewPassword (Read-Host -AsSecureString "Новый пароль")

# Где пользователь сейчас залогинен (на конкретном хосте)
quser /server:<host>
logoff <SessionID> /server:<host>
```

Облако на примере Exchange Online / Microsoft Graph PowerShell **[проверить: актуальные имена командлетов и модулей]**:

```powershell
# Сохранить (до удаления!) правила, включая скрытые, и настройки пересылки
Get-InboxRule -Mailbox <upn> -IncludeHidden | Format-List * > rules_<upn>.txt
Get-Mailbox <upn> | Select-Object ForwardingSmtpAddress,ForwardingAddress,DeliverToMailboxAndForward
Get-MailboxPermission <upn> | Where-Object { $_.User -notlike "NT AUTHORITY*" }
Get-RecipientPermission <upn>

# Аудит за окно
Search-UnifiedAuditLog -UserIds <upn> -StartDate <start> -EndDate <end> -ResultSize 5000

# Методы MFA и OAuth-согласия
Get-MgUserAuthenticationMethod -UserId <upn>
Get-MgUserOauth2PermissionGrant -UserId <upn>

# Отзыв сессий (refresh-токенов)
Revoke-MgUserSignInSession -UserId <upn>
```

Для другого провайдера в плейбук нужно вписать его эквиваленты (консоль или API): где смотреть журнал входов, где правила ящика, как завершить все сессии. Если эквивалента нет — записать «не поддерживается» и компенсирующую меру (например, отключение учётки целиком).

### 3.9. Критерии решений

| Решение | Критерий |
| --- | --- |
| Отключить учётку, а не только сбросить пароль | Подтверждённый TP и одно из: активная сессия атакующего, закрепление (правило, MFA, OAuth), привилегированная учётка, пользователь недоступен при сильном сигнале |
| Только отозвать сессии + принудительная смена пароля при следующем входе | Сильный сигнал не подтверждён, но и не опровергнут, пользователь доступен и находится рядом с управляемым устройством |
| Изолировать хост пользователя | Признаки стилера, RAT или ClickFix в EDR; или корневая причина не найдена, а учётка привилегированная |
| Сначала наблюдать, потом действовать | Только P1 с признаками подготовленного атакующего и решением IM (подготовить пакет одновременных действий); для обычных учёток не применять, риск BEC и рассылки выше |
| Повысить до P1 | Привилегии в AD/облаке/СЗИ, доступ к базе клиентов с признаками чтения или выгрузки, >1 учётки одной кампанией |
| Передать в PB-05 | Учётка имела доступ к ПД, и в окне компрометации есть доступ к ящику/файлам/системам с ПД, либо журналов недостаточно, чтобы это исключить |
| Передать в PB-07 | Действия совершены самим сотрудником с его устройства и противоречат его обязанностям |
| Закрыть как FP | Все признаки FP из 3.2 подтверждены, сильных сигналов нет, обоснование в тикете |

## 4. Ошибки и риски в текущем тексте

| Место в плейбуке | К чему приведёт | Как исправить |
| --- | --- | --- |
| «Удалить чужие устройства MFA и правила пересылки» до сбора артефактов | Потеряны адрес пересылки, условия правила, ID устройства. Не выяснить, какие письма ушли и кому, нет IOC для охоты по компании | Сначала экспорт (3.8), потом удаление |
| «Заблокировать IP атакующего на NGFW» | Для облачной почты бесполезно; при CGNAT — блокировка клиентов магазина; ложное чувство «сдержали» | Блокировка в условном доступе облака и на VPN, после отзыва сессий, с проверкой, что IP не общий |
| Блокировка IP и сброс пароля без порядка и без одновременности | Атакующий видит реакцию и использует оставшийся доступ (токен приложения, сессию VPN, второй ящик) | Порядок 5.6, пакетом |
| Сброс пароля, пока стилер на хосте | Новый пароль уходит атакующему через минуты | Хост в EDR сначала, пароль с чистого устройства |
| Новый пароль или ссылку отправить по почте | Атакующий читает почту | Только телефон или лично |
| Звонок по номеру из подписи письма или из AD | Номер мог поменять атакующий; разговор с ним же | Номер из HR-справочника, при сомнении — через руководителя |
| «Это был он?» как основной вопрос | При AiTM/MFA fatigue пользователь честно говорит «да», TP закрыт как FP | Скрипт 5.4, проверка по журналам независимо от ответа |
| Триаж стоит на звонке | Ночью звонок не проходит, инцидент висит до утра, атакующий рассылает фишинг всю ночь | Ветка «не дозвонились» (5.5) |
| «Включить MFA, если его не было» без контроля регистрации | Атакующий регистрирует свой MFA первым и получает «легальный» второй фактор | Временный код доступа / регистрация при проверке личности |
| Нет учёта Kerberos-билетов и access-токенов | Атакующий работает ещё до 10 часов (AD) или ~1 час (облако) после «сдерживания», команда думает, что всё закрыто | Отключение учётки + завершение сессий + мониторинг после отзыва |
| Нет проверки отправленных писем | Внутренний фишинг от доверенного отправителя распространяет инцидент на другие учётки; BEC-письма контрагентам | Q9 + ветка BEC |
| Нет пивота по инфраструктуре | Масштаб занижен: одну учётку закрыли, ещё три остаются у атакующего | Q6, Q7 обязательны до понижения критичности |
| Отключение сервисной учётки без владельца | Остановка 1С, интеграций сайта, бэкапа | Ветка «сервисная учётка», согласие IM и владельца |
| Отключение учётки руководителя без IM | Конфликт, срыв сделки, «ИБ мешает бизнесу» | Согласование IM, предупреждение руководителя по телефону |
| Переход в PB-05 только «если был доступ к ПД» | Без журналов чтения доступ не доказать и не опровергнуть, решение откладывается, 24 часа истекают | Правило: «нельзя исключить — передаём DPO сейчас» |
| Критерий закрытия «все действия изучены» | Субъективно, инцидент закрывают преждевременно или не закрывают никогда | Проверяемые критерии 5.12 |
| Нет срока хранения облачных журналов в подготовке | Через неделю журналы входов недоступны, хронологию не собрать | Экспорт в первый час |
| Сообщение пользователю «ваша учётка взломана» до проверки | Если это инсайдер — он предупреждён, уничтожает следы | Нейтральная формулировка, ветка PB-07 |
| Нет действий после неудачного spraying | P4 закрывают, хотя одна из учёток «попала» | Обязательная проверка успеха с того же IP |

## 5. Конкретные предложения: что добавить (черновые формулировки)

### 5.1. Шапка

> **PB-03 Компрометация учётной записи сотрудника**
> Версия 0.2 · Владелец: руководитель ИБ · Пересмотр: раз в 6 месяцев и после каждого инцидента по сценарию.
> **Покрывает:** доменные учётки AD, учётки облачной почты и файлов, VPN, внутренние системы (1С, админка сайта), сервисные учётки.
> **Не покрывает:** учётки клиентов интернет-магазина (отдельный плейбук), компрометацию облачного тенанта целиком (PB-10).
> **Связанные:** PB-01 (фишинг как источник), PB-04 и PB-S4 (вредонос на хосте), PB-05 (ПД), PB-07 (инсайдер), PB-10 (облако).
> **ATT&CK:** T1078.002, T1078.004, T1110.001/.003/.004, T1621, T1539, T1550.004, T1557, T1528, T1098.005, T1114.003, T1564.008, T1534, T1555.003.

### 5.2. Матрица критичности

> | Ситуация | Критичность |
> | --- | --- |
> | Подбор/spraying без единого успешного входа | P4 |
> | Подозрительный успешный вход, сильных сигналов нет, пользователь не подтвердил | P3 (до выяснения) |
> | Подтверждённая компрометация обычной учётки | P2 |
> | То же у руководителя или в финансах | P2 + финансовый директор в курсе |
> | Привилегированная учётка AD, облака, СЗИ, бэкапа | P1 |
> | Подтверждённый доступ к базе клиентов / ПД или невозможность его исключить при широком доступе | P1 |
> | Несколько учёток одной кампанией | P1 |
> Критичность пересматривается после пивота по инфраструктуре (Q6) и оценки доступа к данным.

### 5.3. Карточка L1 «первые 15 минут» (одна страница, держать под рукой)

> 1. Завести тикет. Записать: учётка, класс (обычная / VIP / финансы / привилегированная / сервисная), время, IP, страна, ASN, устройство, клиент, был ли MFA.
> 2. Проверить сильные сигналы (список 3.2). Есть хоть один → **сразу L2**. Учётка привилегированная → **сразу L2 и IM**.
> 3. Проверить FP: корпоративный IP? известное устройство? в тикете есть командировка?
> 4. Позвонить пользователю по номеру из HR-справочника, по скрипту. Не писать на почту и в корпоративный мессенджер, если он привязан к той же учётке.
> 5. Не дозвонились за 2 попытки → L2 с пометкой «пользователь недоступен».
> 6. Сам L1 ничего не удаляет и не отключает.

### 5.4. Скрипт звонка пользователю

> «Добрый день, это служба информационной безопасности, [имя]. Мы видим необычную активность и хотим уточнить пару вопросов, это займёт пару минут.»
> 1. Где вы сейчас находитесь и с какого устройства работали сегодня / вчера вечером?
> 2. Пользуетесь ли VPN-сервисами на личных устройствах?
> 3. Приходили ли вам запросы на подтверждение входа, которые вы не ожидали? Нажимали ли вы «подтвердить» хотя бы раз?
> 4. Вводили ли вы в последние дни пароль после перехода по ссылке из письма или сообщения? Вводили ли код с экрана на каком-то сайте?
> 5. Давали ли вы какому-то приложению доступ к почте или файлам?
> 6. Устанавливали ли программы, расширения браузера, «исправляли ошибку» по инструкции с сайта?
> 7. Звонил ли вам кто-то от имени ИТ с просьбой назвать код или сменить пароль?
> Не сообщать: какие IP и страны мы видим, что именно нашли, что будем делать. Ответы записать дословно в тикет со временем звонка.
> Если пользователь подтвердил, что получал неожиданные запросы MFA или вводил пароль по ссылке — считать TP независимо от остальных ответов.
> Если собеседник кажется не тем человеком — прекратить разговор и перезвонить через руководителя.

### 5.5. Дерево триажа L2

> **Шаг 1. Есть сильный сигнал?**
> - Нет, и признаки FP подтверждены → закрыть как FP, предложить исключение в правиле (конкретный IP/ASN/устройство, не страну целиком).
> - Нет, но FP не подтверждён → P3, отозвать сессии (минимальное влияние на бизнес), наблюдать 24 часа по правилам на учётку, повторить звонок в рабочее время.
> - Да → шаг 2.
>
> **Шаг 2. Пользователь подтвердил, что это он?**
> - Да, и действия после входа объяснимы (нет правил, MFA, OAuth, рассылки) → FP с обоснованием.
> - Да, но есть закрепление или действия, которые он не делал → TP (вероятно AiTM / fatigue / кража cookie).
> - Нет → TP.
> - Не дозвонились → решение по силе сигнала: при закреплении (правило, MFA, OAuth) или входе с хостинга с последующими действиями — **TP, сдерживание без ожидания** в пределах полномочий L2 (для привилегированных — с IM по телефону).
>
> **Шаг 3. Классифицировать и выбрать ветку** (5.7). Присвоить критичность по 5.2.
>
> **Шаг 4. Сохранить** (5.8, приоритет 1) → **сдержать** (5.6) → **расследовать масштаб** (2.6, Q5–Q10).

### 5.6. Порядок сдерживания

> Выполнять пакетом, по возможности одним человеком за 10–15 минут, каждое действие со временем в тикете.
> 0. Если признаки стилера на хосте → изолировать хост в EDR (полномочия L2).
> 1. **Сохранить:** экспорт правил ящика (включая скрытые), настроек пересылки, прав на ящик, списка методов MFA, устройств, OAuth-согласий, журналов входов и аудита за окно.
> 2. **Отозвать** все сессии и refresh-токены в облаке; завершить VPN-сессию на шлюзе; завершить сессии на хостах, где учётка залогинена.
> 3. **Отключить** учётку (AD и облако) или, по решению 3.9, сбросить пароль с обязательной сменой. Новый пароль/временный код — только по телефону или лично.
> 4. **Удалить закрепление:** правила, пересылку, чужие права на ящик, чужие методы MFA и устройства, OAuth-согласия, пароли приложений; вернуть телефон/почту для восстановления.
> 5. **Заблокировать инфраструктуру:** IP в условном доступе облака и на VPN (если это не общий IP), домены фишинга на прокси/почтовом шлюзе.
> 6. **Наблюдать** 2 часа: попытки входа в учётку (0xC0000072, ошибки «учётка отключена» в облаке), активность с IP атакующего, новые правила в других ящиках.
> Блокировка IP никогда не является единственным действием сдерживания.

### 5.7. Ветки

> **Привилегированная учётка (P1).** Сразу IM. Резервный канал связи. Помимо 5.6: проверить изменения групп (Q10), новые учётки (4720), изменения GPO, новые SPN, делегирования, задачи на серверах; проверить, не создавал ли атакующий свои учётки и приложения в облаке. Сбросить пароли других административных учёток, с которыми эта учётка работала на одних хостах. Оценить необходимость сброса krbtgt — решение IM, отдельной процедурой **[проверить процедуру]**.
>
> **Сервисная учётка.** Звонить некому — звонить владельцу системы. Не отключать без согласия IM и владельца: сначала выяснить, где пароль используется (конфиги, задачи, службы). Ограничить: запрет интерактивного входа, ограничение по хостам; ротация пароля по плану с владельцем. Искать, откуда учётка использовалась нетипично (хост, тип входа 2/10 у сервисной учётки — сильный сигнал).
>
> **BEC / финансы.** В первый час: выяснить, отправлялись ли письма контрагентам с реквизитами (Q9), подключить финансы: проверить платежи за окно компрометации, при подозрении — звонок в банк для отзыва платежа (время критично). Контрагентам звонить по номеру из договора. Сохранить письма с заголовками.
>
> **MFA fatigue.** Пароль у атакующего уже есть: смена пароля обязательна, даже если ни один push не был подтверждён. Если подтверждён — полный 5.6. Включить number matching, если не включено. Искать, откуда пароль (стилер? утечка?).
>
> **Стилер на хосте.** Хост изолировать (PB-04 / PB-S4). Новый пароль выдать только после очистки/переустановки и с другого устройства. Сменить все пароли, сохранённые в браузере пользователя (рабочие и рекомендовать личные), отозвать сессии во всех сервисах, ротация API-ключей, SSH-ключей, токенов, которые были на хосте.
>
> **AiTM / кража cookie.** Найти письмо-источник, удалить его у всех получателей, найти кликнувших (PB-01), пивот по домену фишинга в прокси. Отзыв сессий важнее смены пароля, но делать оба.
>
> **Массовый spraying.** Без успеха — P4: заблокировать источник в условном доступе, проверить, что никто не вошёл с этого IP (Q1 + Q3), проверить блокировки (4740) — если много учёток заблокировано, это DoS для бизнеса, сообщить ИТ. С успехом — P2/P1, каждая успешная учётка проходит 5.6, координирует IM.
>
> **Пользователь недоступен.** См. 5.5, шаг 2. Оставить пользователю сообщение с просьбой перезвонить на номер SOC (не по почте).
>
> **Инсайдер.** Действия совершены с устройства сотрудника, им самим, вразрез с обязанностями → остановить работу по PB-03, перейти в PB-07. Не звонить сотруднику повторно, не сообщать руководителю без IM, сохранить артефакты.
>
> **Внешний подрядчик.** Связаться через ответственного за договор. Учётку подрядчика можно отключить сразу при TP, согласие IM постфактум **[допущение]**.

### 5.8. Артефакты с приоритетом

> | Приоритет | Что | Почему сейчас |
> | --- | --- | --- |
> | 1 (до любых изменений) | Правила ящика, пересылка, права, методы MFA, устройства, OAuth-согласия | Исчезнут при удалении |
> | 1 | Журналы входов и аудита облака за окно (минимум 30 дней) | Срок хранения у провайдера ограничен |
> | 1 | Атрибуты учётки AD, членство в группах, `repadmin /showobjmeta` | Изменятся при сдерживании |
> | 2 | Отправленные и удалённые письма (удержание ящика / восстанавливаемые элементы) | Атакующий мог удалить |
> | 2 | VPN, NGFW, прокси за окно; события DC (3.3) | Ротация журналов |
> | 2 | Триаж-коллекция EDR с хоста пользователя (при подозрении на стилер — до переустановки) | Переустановка уничтожит |
> | 3 | Объяснение пользователя, скриншоты запросов MFA, письмо-источник с заголовками | Память и почта меняются |
> Каждый экспорт: имя файла, время, кто сделал, хеш SHA-256, место хранения (доступ только у команды реагирования).

### 5.9. Коммуникации и шаблоны

> **Статус IM (P2/P1):**
> «PB-03, INC-___, P_. Учётка: ___ (класс). Окно компрометации: ___–___. Как вошли: ___ (подтверждено / предполагается). Сделано: ___ (время). Атакующий делал: ___. Другие учётки: проверено / найдено ___. ПД: доступ подтверждён / не исключён / исключён. Нужны решения: ___. Следующий статус: ___.»
>
> **Сотрудникам, получившим фишинг из взломанного ящика** (отправляет IM или ИТ, не со взломанного ящика):
> «Коллеги, письмо от [имя] с темой "[тема]", отправленное [дата/время], не было отправлено им. Не открывайте ссылку и вложения. Если вы уже перешли по ссылке или ввели пароль — позвоните в ИБ по номеру ___.»
>
> **Контрагенту (по телефону, по номеру из договора):**
> «С адреса нашего сотрудника [адрес] могли поступить письма об изменении реквизитов или с вложениями. Наши реквизиты не менялись. Пожалуйста, не проводите платежи по новым реквизитам и сообщите, если такое письмо пришло.»
>
> **DPO:** факты (какие данные доступны учётке, какие действия видны в журналах, чего журналы не позволяют установить), время выявления. Решение об уведомлении принимает DPO с IM.

### 5.10. Устранение

> 1. Корневая причина подтверждена артефактом (письмо-источник, процесс стилера, запись в журнале сервис-деска, учётка в утечке). Если не найдена — записать «не установлена» и считать хост пользователя скомпрометированным до проверки.
> 2. Хост очищен или переустановлен (при стилере — переустановка).
> 3. Ротированы все секреты, к которым был доступ у учётки и на хосте.
> 4. Проверено отсутствие закрепления: правила во всех ящиках компании (Q7), новые MFA-методы у всех за окно (Q8), новые учётки и изменения групп (Q10), новые OAuth-приложения в тенанте.
> 5. Закрыт вектор: правило условного доступа / number matching / запрет устаревших протоколов / ужесточение процедуры сервис-деска — то, что применимо.

### 5.11. Восстановление

> 1. Учётку включает ИТ по решению L2 (обычная) или IM (привилегированная, VIP).
> 2. Новый пароль и регистрация MFA — лично или с подтверждением личности по процедуре сервис-деска; временный код доступа ограничен по времени.
> 3. Пользователь проходит короткий разбор: как распознать AiTM-страницу, MFA fatigue, ClickFix. Без поиска виновного.
> 4. Наблюдение 14 дней (по IR-плану не менее 2 недель): правила SIEM на вход учётки из новых ASN/стран, на IOC инцидента, на правила в ящике и новые методы MFA у этой учётки. Ответственный: L2, проверка раз в сутки.

### 5.12. Критерии закрытия (проверяемые)

> - [ ] Все сессии и токены отозваны; после отзыва нет успешных входов с инфраструктуры атакующего (проверено запросом Q5 через 24 часа и через 7 дней).
> - [ ] Закрепление удалено, экспорт до удаления приложен к тикету.
> - [ ] Пивот по IP/ASN/UA выполнен (Q6), другие учётки проверены, результат в тикете.
> - [ ] Отправленная атакующим почта найдена и обработана (получатели предупреждены, письма удалены).
> - [ ] Корневая причина установлена или явно записано, что не установлена, и какие меры компенсируют.
> - [ ] Хост пользователя проверен в EDR, результат в тикете.
> - [ ] Решение по ПД принято DPO и записано (уведомлять / не уведомлять, обоснование).
> - [ ] Правило детекта, которое должно было сработать раньше, создано или скорректировано.
> - [ ] Наблюдение 14 дней назначено с ответственным.

### 5.13. Метрики для отчёта

> - Время от первого действия атакующего до сработки (MTTD).
> - Время от сработки до отзыва сессий (ключевая метрика для этого сценария).
> - Время от сработки до решения DPO по ПД (сравнить с 24 часами).
> - Число затронутых учёток, число отправленных атакующим писем, число кликнувших получателей.
> - Какой источник дал первую сработку (облако, AD, EDR, пользователь).

### 5.14. Типичные ошибки (расширенный список)

> 1. Сменить пароль и забыть про сессии, токены, VPN, пароли приложений и OAuth.
> 2. Удалить правило пересылки, не сохранив его.
> 3. Выдать новый пароль, пока на хосте стилер.
> 4. Поверить «да, это я» при сильных сигналах.
> 5. Не проверить, что атакующий отправил из ящика.
> 6. Не поискать другие учётки с той же инфраструктуры.
> 7. Отключить сервисную учётку без владельца.
> 8. Писать пользователю на скомпрометированную почту.
> 9. Ждать доказательств доступа к ПД, пока идут 24 часа.

## 6. Оценка

| Критерий | Оценка | Обоснование |
| --- | --- | --- |
| Релевантность | **6 / 10** | Правильные ключевые мысли (сессии ≠ пароль, звонок вне почты, MFA-устройства, правила пересылки, связь с ПД). Но модель угроз «украли пароль» отстаёт от 2025–2026 (AiTM, стилеры с cookie, MFA fatigue, OAuth/device code, сервис-деск), блокировка IP на NGFW для облачной почты неэффективна, критерий P1 слишком узкий, гео-триггер без оговорок про FP. |
| Полнота | **3 / 10** | Есть все фазы по названию, но нет ветвлений (ночь, сервисная, привилегированная, BEC, инсайдер, spraying), полномочий на действия с учётками, порядка «сохранить → сдержать», пивота по инфраструктуре, проверки отправленной почты, коммуникаций с контрагентами и финансами, проверяемых критериев закрытия, подготовки (сроки хранения журналов, справочник телефонов). |
| Детализация | **2 / 10** | Два Event ID без полей и кодов, ни одного запроса к SIEM, ни одной команды, ни одного критерия решения, нет таймингов внутри сценария и апрувов. На смене в 3 часа ночи аналитик L1 не поймёт, что считать TP и кому звонить, если пользователь не отвечает; L2 не знает, имеет ли право отключить учётку и что выгрузить до удаления. |

**Итого:** хороший конспект для самопроверки («что не забыть»), но не рабочая инструкция. Минимальный набор, который переводит плейбук в рабочий: критерии TP/FP (3.2), карточка L1 и скрипт звонка (5.3–5.4), дерево триажа с веткой «не дозвонились» (5.5), порядок сдерживания с «сначала сохранить» (5.6), таблица полномочий (2.4), 5–6 базовых запросов (Q1, Q3, Q5, Q6, Q7, Q9) и проверяемые критерии закрытия (5.12). Ветки (5.7) можно добавлять постепенно, начиная с привилегированной учётки, BEC и стилера.

# Ревью PB-04: SOC-аналитик L2 с опытом работы в SOC 5+ лет

Объект ревью: `/mnt/project-files/ir-study/drafts/PB-04-malware-workstation.md` («PB-04 Вредонос на рабочей станции»).
Контекст: учебный IR-план «Альфа-Трейд» (`/mnt/project-files/ir-study/source/ir-plan.md`): роли L1, L2, IM, ИТ, владелец системы, юрист/DPO, PR, директор; критичность P1–P4; СЗИ: NGFW, WAF, антивирус, EDR, SIEM, облачная почта, почтовая песочница.

Условные обозначения:
- **[проверить]** — факт, в котором я не уверен на 100 % или который зависит от вендора / редакции нормативки. Перед использованием сверить с документацией.
- **[учебное]** — цифра или правило, придуманные для учебного примера, а не взятые из стандарта.
- Примеры запросов даны на KQL (Microsoft Defender for Endpoint / Sentinel) и SPL (Splunk) только как иллюстрация логики. В «Альфа-Трейд» вендоры SIEM и EDR не названы; в российских SIEM (MaxPatrol SIEM, KUMA и др.) синтаксис свой, я его здесь не привожу, чтобы не выдумывать.

## 0. Краткий вывод

Плейбук сейчас — это хорошая **памятка на одну страницу**, а не рабочий документ. Направление мысли верное: «антивирус удалил — это не конец», изоляция через EDR с сохранением связи с консолью, поиск того же хеша по парку, переустановка при сомнении. Но в 3 часа ночи L1 по нему не сможет:

- однозначно решить, ложная сработка или нет (нет критериев и полей, на которые смотреть);
- правильно присвоить критичность (нет ветки P1, не учитываются роль пользователя и ценность хоста, нет учёта кражи учётных данных и сессий);
- понять, кого будить и в какой срок (нет таймингов и RACI);
- собрать данные, не уничтожив их (нет порядка сбора, нет запретов «не перезагружать / не сканировать до сбора»);
- оценить, не превратился ли «вредонос на одной станции» в утечку ПДн (152-ФЗ) или в предвестник шифровальщика.

Главные смысловые проблемы:
1. **Модель угроз устарела.** Пример триггера «Word запускает PowerShell» — классика 2017–2021 годов. В 2025–2026 на рабочих станциях доминируют инфостилеры, загрузчики через ClickFix / поддельную CAPTCHA, поддельные обновления браузера, вредоносные инсталляторы из поисковой выдачи и рекламы, архивы/LNK/ISO/HTA, злоупотребление легитимными RMM. Плейбук этого не видит.
2. **«Сбросить пароли» — недостаточно и иногда вредно.** Стилер крадёт cookies и токены сессий, которые переживают смену пароля; пароли из браузера — это пароли ко всему (почта, 1С, админка магазина, VPN, банк-клиент). Сброс с заражённого хоста или до изоляции — ошибка.
3. **Нет ветки P1 и нет связи с 152-ФЗ.** Если на хосте были выгрузки базы клиентов или доступы к ней, это потенциальная утечка ПДн, а значит P1 и часы до уведомления РКН по IR-плану.
4. **Нет порядка работы с уликами.** «Дамп памяти при P2» — поздно и слишком узко; блокировка хеша в EDR до получения образца может удалить образец.

Оценки (подробно в разделе 6): релевантность **5/10**, полнота **3/10**, детализация **2/10**.

## 0.1. Что в плейбуке сделано правильно (оставить)

| Что | Почему это хорошо |
| --- | --- |
| «Антивирус удалил файл — это ещё не конец» и «типичная ошибка» | Это самая частая ошибка L1 в реальных SOC. Хорошо, что вынесено отдельно. |
| Изоляция в EDR с сохранением связи с консолью | Правильный метод: хост не выключается, память сохраняется, можно продолжать сбор. |

| «При сомнении — переустановить ОС из эталонного образа» | Правильный дефолт для рабочих станций: дешевле, чем доказывать чистоту. |
| Градация P4/P3/P2 по факту запуска и наличию C2 | Логика «блокировано до запуска / запустилось / есть C2» верная как основа. |
| Критерий закрытия «путь проникновения известен» | Правильно требовать корневую причину, а не только удаление файла. |

## 1. Релевантность (соответствие практике SOC/IR 2025–2026)

### 1.1. Что соответствует практике
- Общий каркас: триаж → скоупинг → изоляция → блокировка IOC → переустановка → наблюдение.
- Ставка на EDR как главный инструмент (дерево процессов, изоляция, блокировка).
- Ссылки на MITRE ATT&CK.

### 1.2. Что устарело или неточно

**1) Пример триггера «Word запускает PowerShell».**
Microsoft с 2022 года по умолчанию блокирует VBA-макросы в файлах с отметкой «из интернета» (Mark of the Web). Атакующие массово ушли на другие цепочки. Сценарий с макросом остаётся возможным (старые версии Office, файлы без MotW, документы из внутренних источников), но как единственный пример он вводит в заблуждение. Актуальные цепочки, которые должен узнавать L1:

| Цепочка | Как выглядит в EDR | ATT&CK |
| --- | --- | --- |
| ClickFix / поддельная CAPTCHA / «исправьте ошибку» | `explorer.exe` → `powershell.exe` / `mshta.exe` / `cmd.exe` с длинной командой; запись в `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\RunMRU` | T1204.004 [проверить номер подтехники], T1059.001, T1218.005 |
| Поддельное обновление браузера, SEO-отравление, вредоносная реклама | браузер → загрузка `.zip`/`.msi`/`.exe`/`.js` → `wscript.exe`/`msiexec.exe` → дочерние процессы | T1189, T1204.002 |
| Архив / ISO / LNK / HTA во вложении | `outlook.exe` или `explorer.exe` → `7zFM.exe`/`WinRAR.exe` → `.lnk` → `cmd`/`powershell`/`mshta` | T1566.001, T1204.002 |
| HTML smuggling | браузер сохраняет архив, собранный из HTML-вложения, без прямой загрузки по URL | T1027.006 |
| DLL sideloading | подписанный легитимный `.exe` в `%AppData%`/`%Temp%` грузит соседнюю неподписанную DLL | T1574.002 |
| Злоупотребление RMM (AnyDesk, ScreenConnect и т. п.) | установка легитимного средства удалённого доступа, которого нет в разрешённом ПО | T1219 |
| Инфостилер | чтение файлов профилей браузеров (`Login Data`, `Cookies`, `Local State`), кошельков, Telegram; короткая сессия и выгрузка на HTTP(S) / в Telegram API / на файлообменник | T1555.003, T1539, T1005, T1041, T1567 |
| Отключение защиты (BYOVD и др.) | установка уязвимого драйвера, остановка агента EDR/АВ, пропадание телеметрии | T1562.001, T1068 |

**2) Набор техник ATT&CK слишком узкий.** Указаны только T1204 и T1071. Для этого сценария нужны как минимум: T1566 (фишинг), T1189 (drive-by), T1059 (интерпретаторы), T1218 (LOLBins: `mshta`, `rundll32`, `regsvr32`), T1547.001 (Run-ключи / автозагрузка), T1053.005 (задачи планировщика), T1543.003 (службы), T1555 / T1539 (кража учётных данных и cookies), T1003.001 (LSASS), T1105 (догрузка инструментов), T1562 (отключение защиты), T1021 (боковое перемещение), T1041 / T1567 (эксфильтрация).

**3) Модель «вредонос = файл с хешем».** Блокировка по хешу и поиск по хешу работают против массовых образцов, но современные загрузчики пересобираются под каждую жертву, а вторая стадия часто выполняется в памяти (PowerShell, .NET, shellcode). Нужен поиск по **поведению** (родитель → потомок, командная строка, пути, домены), а не только по хешу.

**4) Градация критичности не учитывает главное в 2025–2026 — кражу учётных данных.** Типичный современный случай: стилер отработал 30 секунд, AV/EDR его убил, C2 «больше нет», хост один → по плейбуку P3. В реальности это может быть самый опасный сценарий: украдены сессии облачной почты, пароль от VPN, доступ к админке магазина, к 1С, к банк-клиенту. По IR-плану такие последствия тянут на P2 (взломанная учётка) или P1 (ПДн, AD).

**5) «Сбросить пароли пользователя» как стандарт устарел.** Сброс пароля не отзывает уже выданные токены и cookies в облачных сервисах (поведение зависит от провайдера) [проверить для облачной почты «Альфа-Трейд»]. Современная практика: отозвать сессии/токены, сменить пароль с чистого устройства, проверить MFA-методы, правила пересылки, приложения с доступом к почте.

**6) «Дамп памяти при P2» — поздно и неверно по логике.** Критичность P2 часто становится ясна именно после анализа памяти или после того, как найден C2. Если ждать P2, к моменту решения процесс уже завершится или хост перезагрузят.

**7) Нет связи с другими плейбуками.** Сценарий «вредонос на станции» почти всегда пересекается с PB-01 (фишинг), PB-02 (шифровальщик), PB-03 / PB-10 (компрометация учётки / облачной учётки), PB-05 (утечка), PB-S3 / PB-S4 (сработки АВ / EDR). Должно быть явно сказано, когда и в какой плейбук переключаться.

## 2. Полнота: что пропущено

Ниже — всё, что, на мой взгляд, должно быть в полноценном плейбуке такого типа. Отмечено, есть ли это сейчас.

### 2.1. Шапка и паспорт плейбука
| Элемент | Есть? |
| --- | --- |
| Идентификатор, версия, дата, владелец плейбука, дата следующего пересмотра | Нет |
| Область применения: какие ОС (Windows / macOS / Linux-станции разработчиков), корпоративные и личные устройства, удалённые ноутбуки | Нет |
| Что НЕ входит (шифровальщик → PB-02, сервер → отдельный плейбук, потерянное устройство → PB-09) | Нет |

| Связанные плейбуки и точки переключения | Нет |
| RACI (кто делает, кто утверждает, кого информировать) | Нет |
| Тайминги по фазам | Нет |

### 2.2. Подготовка (предусловия), которых нет
- Аудит Windows: включено ли журналирование командной строки в 4688, PowerShell Script Block Logging (4104), Sysmon (или аналогичная телеметрия EDR), аудит задач планировщика (4698) — иначе половина проверок невозможна.
- Список «золотых» хостов и VIP/привилегированных пользователей (бухгалтерия с банк-клиентом, администраторы домена, администраторы сайта, разработчики, директор) — для повышения критичности.
- Список разрешённого ПО и RMM — чтобы отличать легитимный AnyDesk от закладки.
- Утверждённые инструменты сбора (EDR live response, KAPE / Velociraptor, WinPmem / Magnet RAM Capture) и место хранения улик.
- Права L1/L2 в EDR и на NGFW: кто может изолировать, блокировать хеш/домен, запускать live response.
- Внутренняя песочница (почтовая песочница из IR-плана) и правило «не загружать образцы в публичные сервисы».
- Контакт банка для экстренной блокировки платежей (если на хосте бухгалтерии банк-клиент).
- Процедура для удалённых ноутбуков без VPN: что делать, если агент EDR не на связи.
- Эталонный образ ОС и процедура переустановки, сроки выдачи подменного ноутбука.

### 2.3. Триаж — пропущенные проверки
1. **Здоровье агентов:** агент EDR/АВ на хосте онлайн? Когда последний раз выходил на связь? Нет ли событий отключения защиты, добавления исключений?
2. **Какое действие выполнил АВ:** «удалён», «в карантине», «вылечен», «обнаружен, действие не выполнено», «ошибка лечения». Это разные исходы.
3. **Тип детекта:** вредонос / потенциально нежелательное ПО (PUA, «not-a-virus», adware) / хакерская утилита (HackTool) / эвристика / тестовый файл (EICAR). Разная критичность и разная обработка.
4. **Путь файла как индикатор стадии:** `Downloads` / кэш браузера / вложение в `Temp\Outlook` — до запуска; `%AppData%`, `%LocalAppData%\Temp\<random>`, `%ProgramData%`, `C:\Users\Public` — скорее всего, уже после запуска / распаковки.
5. **Источник файла:** Zone.Identifier (HostUrl / ReferrerUrl), письмо (через трассировку почты), URL в журналах NGFW/прокси, USB.
6. **Контекст пользователя:** роль, привилегии, доступ к ПДн / 1С / админке сайта / банк-клиенту, локальный администратор или нет.
7. **Контекст хоста:** офис / удалёнка, VPN, ОС, критичность, были ли похожие сработки за 30 дней.
8. **Признаки «руки на клавиатуре»:** разведка (`whoami`, `net group "domain admins" /domain`, `nltest /dclist`, `ipconfig /all`, `systeminfo`, AdFind / SharpHound), доступ к LSASS, инструменты удалённого управления, Cobalt Strike / Sliver / прочие фреймворки → это предвестник шифровальщика, P1/P2 и переход в PB-02.
9. **Признаки кражи учётных данных:** обращение не-браузерного процесса к файлам профиля браузера; архивация и выгрузка; обращения к `api.telegram.org` / файлообменникам с хоста, где Telegram не используется.
10. **Интервью с пользователем** (по телефону, не через почту/мессенджер на заражённом хосте): что открывал, что вводил, вставлял ли команду из браузера в «Выполнить», подключал ли флешку, видел ли странные окна.
11. **Проверка на ложное срабатывание:** подписан ли файл, известное ли ПО, совпадает ли поведение с легитимным (скрипты ИТ, обновлятели, средства администрирования).

### 2.4. Скоупинг — пропущенные измерения
Сейчас есть только «тот же хеш и C2 на других хостах». Нужно расширить по осям:
- **Файл:** хеш, имя, путь, подпись, размер — по всему парку за 30–90 дней.
- **Сеть:** домены, IP, URL, JA3/JA4 и SNI (если NGFW это пишет [проверить]) — в журналах NGFW, DNS, прокси.
- **Почта:** то же письмо / отправитель / вложение / ссылка у других получателей → удаление из ящиков (PB-01).
- **Пользователь:** куда ещё входила эта учётка после времени заражения (рабочие станции, серверы, VPN, облачная почта, 1С); не было ли входов из необычных стран/ASN.
- **Хост:** кто ещё входил на этот хост (особенно администраторы — их хеши/билеты могли быть в памяти).
- **Поведение:** та же командная строка / тот же родитель → потомок на других хостах.
- **Время:** окно поиска — от первого появления файла минус запас (≥ 7 дней), а не от времени сработки.

### 2.5. Сдерживание — пропущенные решения
- Когда изолировать сразу, а когда сначала наблюдать (для целевой атаки иногда сначала собирают картину, чтобы не спугнуть; для массового вредоноса — изолировать сразу).
- Что делать, если хост офлайн / вне VPN / без EDR.
- Отзыв сессий и токенов в облачной почте, VPN, SSO; проверка правил пересылки и MFA.
- Блокировка домена/URL, а не только IP; проверка, не общий ли это IP (CDN, хостинг) перед блокировкой.
- Отдельные действия для бухгалтерии (банк-клиент), администраторов сайта, привилегированных учёток.
- Блокировка учётки vs смена пароля: что и в каком порядке, кто выполняет.
- Повторная блокировка, если вредонос вернулся после изоляции.

### 2.6. Устранение — пропущено
- Перечень мест закрепления, которые нужно проверить (см. 3.6).
- Решение «чистка vs переустановка» с критериями.
- Корневая причина: письмо, сайт, флешка, уязвимость, установленное пользователем ПО.
- Закрытие вектора: блок отправителя/домена, правило в почтовом шлюзе, блок категории в NGFW, запрет запуска из `%AppData%` (AppLocker/WDAC), отзыв локальных админ-прав.

### 2.7. Восстановление — пропущено
- Как переносить данные пользователя (риск вернуть вредоносный файл из «Документов» или облака).
- Перевыпуск/повторная регистрация агентов EDR/АВ, проверка, что телеметрия идёт.
- Кто снимает изоляцию и по каким критериям, чей апрув.
- Срок и правила усиленного мониторинга (IR-план требует ≥ 2 недель для инцидентов).

### 2.8. Коммуникации — пропущено
- Уведомление пользователя и его руководителя (что делать / не делать).
- ИТ (переустановка, подменный ноутбук).
- Юрист/DPO при признаках доступа к ПДн → оценка 152-ФЗ.
- Банк — при угрозе банк-клиенту.
- Владелец системы — если украдены доступы к его системе (сайт, 1С).
- Шаблоны сообщений и запрет обсуждать инцидент через возможно скомпрометированную почту пользователя.

### 2.9. Улики и документирование — пропущено
- Порядок сбора по летучести, хеширование улик, место хранения, кто имеет доступ (цепочка хранения).
- Обязательные поля тикета и хронология в UTC (или явно UTC+3, как в шаблоне IR-плана — главное единообразно).
- Требования к образцу: в запароленном архиве (принятый в индустрии пароль `infected`), не на общем диске.

### 2.10. Разбор и улучшения — пропущено
- Какие детекты добавить/поправить по итогам (ссылка на сработку, которая не сработала).
- Метрики: время от сработки до триажа, до изоляции, до переустановки.
- Обратная связь в обучение пользователей.

## 3. Детализация: где слишком общо и что расписать

### 3.1. Триггеры — расписать конкретно
Сейчас: «детект антивируса; поведенческая сработка EDR; NGFW видит обращения к C2». Нужно перечислить сработки по источникам с минимальной критичностью по умолчанию:

| Источник | Сработка / событие | Стартовая критичность [учебное] |
| --- | --- | --- |
| АВ | Детект, действие «удалён/карантин», путь в `Downloads`/вложении, процесс не запускался | P4 |
| АВ | Детект в `%AppData%`/`%Temp%`/`ProgramData` или детект в памяти | P3 |
| АВ | «Действие не выполнено», «ошибка лечения» | P3 |
| АВ | Повторный детект того же семейства на хосте за 7 дней | P3 |
| АВ | HackTool (Mimikatz, Rubeus, AdFind, Impacket и др.) | P2 |
| АВ / EDR | Защита отключена, добавлено исключение, остановлен агент | P2 |
| EDR | Office / архиватор / браузер / `explorer` → интерпретатор (`powershell`, `cmd`, `wscript`, `cscript`, `mshta`, `rundll32`, `regsvr32`) с подозрительной командной строкой | P3 |
| EDR | Доступ к памяти LSASS, дамп учётных данных | P2 (P1 если учётка админа домена) |
| EDR | Стилер: не-браузерный процесс читает `Login Data` / `Cookies` | P2 |
| EDR | Фреймворк пост-эксплуатации (Cobalt Strike, Sliver и т. п.), разведка домена | P2 → оценка P1, переход в PB-02 |
| NGFW / DNS | Обращение к известному C2 / адресу из TI с высокой уверенностью | P3, P2 при регулярном маяковании |
| NGFW / DNS | Только DNS-запрос к домену из TI без соединения | P4 / P3 по контексту |
| Почтовая песочница | Вредоносный вердикт по уже доставленному письму, которое открыли | P3, PB-01 |

### 3.2. Критичность — матрица вместо одной строки
Предлагаю явную матрицу повышения (поверх IR-плана, критичность берётся по худшему признаку):

| Признак | Критичность |
| --- | --- |
| Блокировано до запуска, файл не исполнялся, других хостов нет | P4 |
| Запуск подтверждён, один хост, нет C2, нет кражи учётных данных | P3 |
| Есть C2 (успешные соединения) **или** признаки кражи учётных данных/cookies **или** HackTool **или** отключение защиты | P2 |
| Больше одного хоста, боковое перемещение | P2 |
| Пользователь / хост из списка привилегированных (админы домена, админы сайта, ИТ, бухгалтерия с банк-клиентом, директор) + запуск подтверждён | P2 минимум |
| Затронута учётка админа домена / признаки доступа к AD (DCSync, LSASS на хосте админа) | P1 |
| Признаки доступа к ПДн клиентов или их выгрузки с хоста | P1 + юрист/DPO |
| Предвестники шифровальщика (фреймворк C2 + разведка + отключение защиты) | P1, переход в PB-02 |

### 3.5. Примеры запросов
Даны как иллюстрация логики; адаптировать к SIEM/EDR «Альфа-Трейд». Окно времени, имена индексов и полей — условные.

**а) Распространённость хеша (KQL, MDE):**
```kql
let h = "<SHA256>";
union DeviceFileEvents, DeviceProcessEvents, DeviceImageLoadEvents
| where Timestamp > ago(30d)
| where SHA256 == h or InitiatingProcessSHA256 == h
| summarize first=min(Timestamp), last=max(Timestamp), events=count() by DeviceName, FileName, FolderPath
```

**б) Офис / архиватор / браузер / explorer порождают интерпретаторы (KQL):**
```kql
DeviceProcessEvents
| where Timestamp > ago(7d)
| where InitiatingProcessFileName in~ ("winword.exe","excel.exe","powerpnt.exe","outlook.exe","onenote.exe",
        "winrar.exe","7zfm.exe","explorer.exe","chrome.exe","msedge.exe","firefox.exe")
| where FileName in~ ("powershell.exe","pwsh.exe","cmd.exe","wscript.exe","cscript.exe","mshta.exe",
        "rundll32.exe","regsvr32.exe","msiexec.exe","certutil.exe","bitsadmin.exe","curl.exe")
| project Timestamp, DeviceName, AccountName, InitiatingProcessFileName, FileName, ProcessCommandLine
```
`explorer.exe → powershell` даёт много шума (ярлыки, админы); фильтровать по признакам в командной строке: `-enc`, `-w hidden`, `iex`, `iwr`, `DownloadString`, `FromBase64String`, `http`, `mshta http`.

**в) ClickFix — что вводилось в «Выполнить» (KQL):**
```kql
DeviceRegistryEvents
| where Timestamp > ago(7d)
| where RegistryKey has @"\Explorer\RunMRU"
| where RegistryValueData has_any ("powershell","mshta","cmd","curl","http")
| project Timestamp, DeviceName, InitiatingProcessAccountName, RegistryValueData
```

**г) То же в Sysmon (SPL):**
```spl
index=sysmon EventCode=1 earliest=-7d
  (ParentImage="*\\WINWORD.EXE" OR ParentImage="*\\EXCEL.EXE" OR ParentImage="*\\OUTLOOK.EXE" OR ParentImage="*\\explorer.exe")
  (Image="*\\powershell.exe" OR Image="*\\mshta.exe" OR Image="*\\wscript.exe" OR Image="*\\cmd.exe" OR Image="*\\rundll32.exe")
| search CommandLine="*-enc*" OR CommandLine="*http*" OR CommandLine="*FromBase64String*" OR CommandLine="*IEX*"
| table _time host User ParentImage Image CommandLine
```

**д) PowerShell Script Block с признаками загрузчика (SPL):**
```spl
index=wineventlog source="*PowerShell/Operational" EventCode=4104 earliest=-7d host=<HOST>
  ("FromBase64String" OR "DownloadString" OR "Net.WebClient" OR "Invoke-WebRequest" OR "IEX" OR "Reflection.Assembly")
| table _time host ScriptBlockText
```

**е) Сетевые IOC по всему парку (SPL, NGFW + DNS):**
```spl
(index=ngfw OR index=dns) earliest=-30d (dest_ip IN (<IP1>,<IP2>) OR query IN ("<domain1>","<domain2>") OR url="*<domain1>*")
| stats min(_time) as first max(_time) as last count sum(bytes_out) as bytes_out by src_ip, dest_ip, query, action
```

**ж) Маякование (beaconing) с хоста — грубая эвристика (SPL):**
```spl
index=ngfw src_ip=<HOST_IP> earliest=-24h action=allowed
| sort 0 _time
| streamstats current=f last(_time) as prev by dest_ip
| eval delta=_time-prev
| stats count avg(delta) as avg_int stdev(delta) as sd_int by dest_ip, dest_port
| where count>20 AND sd_int < avg_int*0.2
```
Это эвристика: CDN, обновления и мессенджеры тоже «маякуют». Результат — повод смотреть глазами, а не вердикт.

**з) Куда входила учётка пользователя после времени заражения (SPL):**
```spl
index=wineventlog EventCode=4624 TargetUserName=<user> earliest=<T_infection>
| stats min(_time) max(_time) count by host, LogonType, IpAddress
```
Плюс входы в облачную почту и VPN за тот же период — вручную в их консолях / журналах.

**и) Кто ещё входил на заражённый хост (возможная кража привилегированных учёток) (SPL):**
```spl
index=wineventlog host=<HOST> (EventCode=4624 OR EventCode=4648) earliest=-14d
| where LogonType IN (2,10,11) OR EventCode=4648
| stats count min(_time) max(_time) by TargetUserName, LogonType
```

**к) Стилер: не-браузерный процесс читает профиль браузера (KQL — набор доступных событий о чтении файлов в MDE ограничен [проверить]; в EDR других вендоров это может быть отдельный детект):**
```kql
DeviceFileEvents
| where Timestamp > ago(7d)
| where FolderPath has_any (@"\User Data\Default\Login Data", @"\User Data\Default\Network\Cookies", @"\User Data\Local State")
| where InitiatingProcessFileName !in~ ("chrome.exe","msedge.exe","firefox.exe","browser.exe")
| project Timestamp, DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath, FolderPath, ActionType
```

### 3.6. Live response: что собрать и какими командами
Принцип: **лучше средствами EDR (live response / сбор пакета), чем руками на хосте.** Каждая команда меняет состояние системы — фиксировать в тикете время и что запускалось. Порядок — по убыванию летучести (RFC 3227): память → сеть и процессы → автозапуск → журналы и файловая система.

Через консоль EDR или, если её нет, на изолированном хосте под отдельной учётной записью реагирования (не доменного администратора):
```powershell
# Процессы с родителем и командной строкой
Get-CimInstance Win32_Process | Select-Object ProcessId,ParentProcessId,Name,ExecutablePath,CommandLine,CreationDate | Export-Csv C:\IR\proc.csv -NoTypeInformation
# Сетевые соединения с PID
Get-NetTCPConnection | Select-Object LocalAddress,LocalPort,RemoteAddress,RemotePort,State,OwningProcess,CreationTime | Export-Csv C:\IR\net.csv -NoTypeInformation
Get-DnsClientCache | Export-Csv C:\IR\dnscache.csv -NoTypeInformation
# Задачи планировщика и службы
Get-ScheduledTask | Select-Object TaskPath,TaskName,State,@{n='Action';e={$_.Actions.Execute + ' ' + $_.Actions.Arguments}} | Export-Csv C:\IR\tasks.csv -NoTypeInformation
Get-CimInstance Win32_Service | Select-Object Name,State,StartMode,PathName,StartName | Export-Csv C:\IR\services.csv -NoTypeInformation
# Run-ключи
Get-ItemProperty 'HKLM:\Software\Microsoft\Windows\CurrentVersion\Run','HKCU:\Software\Microsoft\Windows\CurrentVersion\Run','HKLM:\Software\Microsoft\Windows\CurrentVersion\RunOnce','HKCU:\Software\Microsoft\Windows\CurrentVersion\RunOnce'
# Откуда пришёл файл (Mark of the Web)
Get-Content -Path '<путь к файлу>' -Stream Zone.Identifier
```
Классические `tasklist /v` и `netstat -anob` тоже работают. `wmic` в новых сборках Windows 11 отключён по умолчанию / выводится из употребления [проверить] — в плейбук его лучше не включать.

Автозапуск целиком — Sysinternals Autoruns в консольном режиме:
```
autorunsc.exe -accepteula -a * -c -h -s -m > C:\IR\autoruns.csv
```
(`-a *` все категории, `-c` CSV, `-h` хеши, `-s` проверка подписи, `-m` скрыть записи Microsoft — флаги по памяти [проверить по `autorunsc -?`].)

Память: WinPmem / Magnet RAM Capture / DumpIt или встроенная функция EDR — **до** перезагрузки, выключения и до полного сканирования АВ. Дамп писать на внешний носитель или сетевой ресурс улик, не на системный диск, если есть возможность.

Триаж-пакет диска (KAPE или Velociraptor offline collector): журналы `.evtx`, Prefetch, Amcache, ShimCache (SYSTEM hive), SRUM, LNK и Jump Lists, `$MFT`, `$UsnJrnl:$J`, история браузеров (`%LocalAppData%\Google\Chrome\User Data\Default\History`, аналогично Edge / Яндекс.Браузер), содержимое `%AppData%`, `%LocalAppData%\Temp`, `%ProgramData%`, `C:\Users\Public`, папки автозагрузки, карантин АВ.

Места закрепления, которые проверяет L2 перед решением «чистить или переустанавливать»:
- Run / RunOnce (HKLM, HKCU), папки Startup;
- задачи планировщика (`C:\Windows\System32\Tasks`, 4698);
- службы (7045 / 4697);
- WMI-подписки (`Get-CimInstance -Namespace root\subscription -ClassName __EventFilter`, `__EventConsumer`, `__FilterToConsumerBinding`);
- расширения браузеров (особенно установленные вне магазина);
- установленные RMM-средства;
- новые локальные учётки и изменения группы Administrators;
- подмена ярлыков (LNK с изменённым Target), DLL рядом с легитимными `.exe` в пользовательских папках;
- изменения политик Defender / исключения АВ.

### 3.7. Критерии решений (сейчас их нет совсем)

**Ложная или нет (L1):**
- FP: детект на подписанный известный файл легитимного вендора, поведение совпадает с документированным; тестовый файл EICAR от ИТ; известная админская утилита в руках ИТ по заявке. → закрыть, указать обоснование, предложить исключение (утверждает L2, не L1).
- Benign TP: PUA/adware, установленное пользователем без вреда (тулбары, «оптимизаторы») → удаление, P4, сообщение руководителю/ИТ про нарушение политики ПО.
- TP: всё остальное, а также любая неопределённость. **Неизвестный хеш ≠ чистый.** «0 детектов в TI» — не аргумент для закрытия.

**Был ли запуск:**
- Есть события процесса с этим хешем/путём (Sysmon 1 / 4688 / EDR) → да.
- Есть Prefetch / Amcache для файла → вероятно да [Amcache сам по себе не всегда доказывает запуск — проверить].
- Детект только при записи файла в `Downloads`/кэш, нет процесса, нет дочерних файлов → вероятно нет.
- Детект в памяти или в `%Temp%\<random>` после архиватора → да.

**Изолировать или нет:**
- Изолировать сразу: подтверждённый запуск + (C2 или кража учётных данных или HackTool или разведка или отключение защиты), либо любой признак шифровальщика.
- Можно не изолировать: P4 (блокировано до запуска), подтверждено отсутствием процесса и сетевых событий.
- Сначала согласовать с IM: VIP-пользователь в момент критичного бизнес-процесса, хост кассы/склада/производственного процесса, или когда есть основания считать атаку целевой и нужна одномоментная зачистка.

**Чистка или переустановка:**
- Чистка допустима только для P4 и для Benign TP (PUA), при полностью понятной цепочке и отсутствии закрепления.
- Переустановка обязательна: подтверждённый запуск неизвестного/полиморфного вредоноса, загрузчик / второй этап, RAT / C2-фреймворк, стилер, отключение защиты, любые сомнения.

**Когда закрыть:**
- Вектор установлен (или зафиксировано «не установлен» с обоснованием и согласием IM);
- скоупинг по всем осям (2.4) выполнен, результаты в тикете;
- учётные данные и сессии обработаны (см. 5.4);
- хост переустановлен / очищен, агенты работают, изоляция снята с апрувом L2;
- IOC добавлены в блок-листы и в правила SIEM на срок наблюдения;
- для P1/P2 — назначена встреча по разбору.

### 3.8. Тайминги [учебное]
IR-план задаёт только «реакцию до» (P2 — 1 час, P3 — 4 часа). Для этого плейбука нужны внутренние контрольные точки:

| Этап | P2 | P3 | P4 |
| --- | --- | --- | --- |
| L1 взял сработку | ≤ 15 мин | ≤ 30 мин | рабочий день |
| L1 закончил первичный триаж и эскалировал | ≤ 30 мин | ≤ 2 ч | — |
| L2 принял и решил по изоляции | ≤ 30 мин от эскалации | ≤ 1 ч | — |
| Летучие данные собраны | ≤ 1 ч от изоляции | ≤ 4 ч | — |
| Сессии/пароли пользователя обработаны | ≤ 1 ч от подтверждения кражи | ≤ 1 рабочий день | — |
| Скоупинг по парку | ≤ 4 ч | ≤ 1 рабочий день | по хешу ≤ 1 рабочий день |
| Статус IM | каждые 2 ч / дважды в день (по IR-плану) | при закрытии | — |

Отдельный вопрос к IR-плану: в 3 часа ночи при активном C2 ждать L2 до часа — долго. Предлагаю заранее разрешить L1 изоляцию одной рабочей станции по жёстким критериям (запуск подтверждён + успешные соединения с C2 / признаки стилера), с обязательным звонком L2 сразу после. Сейчас IR-план даёт это право только L2 — значит, это изменение плана, решает IM.

### 3.9. RACI (R — делает, A — утверждает, C — консультирует, I — информируется)

| Действие | L1 | L2 | IM | ИТ | Владелец системы | Юрист/DPO | Пользователь/руководитель |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Триаж, вердикт TP/FP, критичность | R | A | I (P2+) | | | | |
| Закрытие как FP + предложение исключения | R | A | | | | | |
| Изоляция одной станции | (R по критериям, если разрешено) | R/A | I | I | | | I |
| Изоляция > 1 станции / хоста VIP / критичного процесса | | R | A | C | C | | I |

## 4. Ошибки и риски в текущей редакции

| № | Формулировка в плейбуке | Риск | Как исправить |
| --- | --- | --- | --- |
| 1 | «Сбросить пароли пользователя хоста: вредонос мог их украсть» | (а) если пользователь меняет пароль на заражённом хосте — новый пароль уйдёт кейлоггеру/стилеру; (б) сброс до изоляции предупреждает атакующего; (в) сброс пароля не отзывает украденные cookies/токены — атакующий остаётся в облачной почте; (г) не учтены все остальные пароли, сохранённые в браузере (VPN, 1С, админка сайта, личные). | Порядок: изолировать → отозвать сессии/токены → сменить пароль с чистого устройства силами ИТ → проверить MFA-методы и правила почты → составить список сервисов из хранилища паролей браузера и сменить пароли по нему. |
| 2 | «Заблокировать хеш в EDR» сразу после изоляции | Блокировка/карантин может удалить единственный экземпляр образца, а без образца нет IOC второго этапа. | Сначала получить образец (карантин / EDR file retrieval), посчитать SHA256, затем блокировать. |
| 3 | «C2-адреса на NGFW» — только адреса | Блок общего IP (CDN, облачный хостинг) может положить легитимные сервисы, в т. ч. для самого магазина. Блок только IP не помогает против смены IP. | Блокировать прежде всего домен/URL/SNI; IP — после проверки, что он не общий; блок IP CDN — только с апрувом IM. |
| 4 | «Дамп памяти при P2» | Дамп не снимут на P3, где он нужен, чтобы понять, P2 ли это. Пропадут бесфайловые стадии и ключи. | «Дамп памяти при подтверждённом запуске, если процесс ещё жив или есть признаки работы в памяти, до перезагрузки — на любом уровне от P3». |

| 6 | «Проверить хеш файла по разведданным» без оговорок | L1 загрузит **файл** (а не хеш) на публичный сервис: (а) атакующий видит, что образец обнаружен; (б) если это документ с данными компании/ПДн — утечка. | «Проверять только по хешу. Загружать файл — только во внутреннюю песочницу или с разрешения L2». |
| 7 | Нет ветки «хост офлайн / без EDR» | Изоляция в EDR не применится к ноутбуку вне сети; плейбук молчит, аналитик ждёт. | Ветка: блок учётки/сессий + блок на NGFW/VPN + звонок пользователю «отключите Wi-Fi, не выключайте» + изоляция при выходе агента на связь. |
| 8 | P2 «если есть связь с C2» | Нет различения DNS-запроса, заблокированного соединения и успешной сессии с передачей данных — L1 будет либо завышать, либо занижать. | Критерий: успешные соединения (`action=allowed`, ненулевой `bytes_out`), повторяющиеся — P2; только DNS / только заблокированные — P3 с анализом. |

| 10 | «Уведомить: IM при P2 или если затронуто больше одного хоста» | Не уведомлены: юрист/DPO (ПДн), ИТ (переустановка), владелец системы (украдены его доступы), бухгалтерия/банк. | Таблица уведомлений по условиям (см. 5.6). |
| 11 | Нет правила канала связи | Если общаться с пользователем через корпоративную почту/мессенджер на заражённом хосте, атакующий увидит. | «С пользователем — только по телефону. Не писать о сработке на его почту и в его мессенджер на этом устройстве». |
| 12 | «Потом снять изоляцию» без условий | Изоляция снимется до переустановки, вредонос возобновит C2. | Снимать только после переустановки или подтверждённой чистки, с апрувом L2, при работающем агенте EDR. |
| 13 | Нет предупреждения о данных пользователя при переустановке | Перенос «Документов» вернёт исходный вредоносный файл; синхронизация облачного диска вернёт его тоже. | Перед восстановлением — проверка данных АВ/EDR, исключение исходного файла; проверить облачные файлы пользователя на тот же хеш. |
| 14 | Нет проверки исключений и отключения АВ | Вредонос мог добавить исключение (5007) — после «очистки» он снова работает незаметно. | Обязательная проверка политик/исключений АВ на хосте и на сервере управления. |
| 15 | Блокировка/изоляция при целевой атаке без координации | Атакующий понимает, что его нашли, и ускоряется (например, запускает шифрование) через другие закрепления. | Для признаков целевой атаки: решение IM о «одномоментной» зачистке — изоляция всех хостов, блок IOC, сброс учёток в одно окно. |

## 5. Конкретные предложения: что добавить (черновые формулировки)

### 5.1. Новая структура документа
```

  0. Паспорт (версия, владелец, область, связанные плейбуки, дата пересмотра)
  1. Предусловия (что должно быть настроено)
  2. Триггеры и стартовая критичность (таблица)
  3. Матрица критичности и повышения
  4. Немедленные действия и запреты (первые 15 минут)
  5. Триаж L1: чек-лист + поля тикета + критерии TP/FP + эскалация
  6. Анализ L2: дерево процессов, вектор, запуск, C2, кража учётных данных, закрепление
  7. Скоупинг по осям (файл, сеть, почта, пользователь, хост, поведение)
  8. Сдерживание (ветки: онлайн / офлайн / без EDR / VIP / целевая атака)
  9. Учётные данные и сессии
```

### 5.2. Блок «Немедленные действия и запреты» (черновик)
> **Первые 15 минут (L1).**
> 1. Зарегистрировать тикет, записать время сработки и время начала работы (UTC).
> 2. Проверить в консоли EDR, что агент на хосте онлайн. Если офлайн — перейти к ветке 8.3.
> 3. Определить, был ли запуск (раздел 5, критерии). Если запуск подтверждён и есть хотя бы один признак P2 — немедленно позвонить дежурному L2 (не только тикет).
> 4. Не связываться с пользователем через почту и мессенджер на этом хосте.
>
> **Запрещено до разрешения L2:** перезагружать и выключать хост; запускать полное сканирование и лечение; вручную удалять файлы; переустанавливать ОС; загружать файл (не хеш) в публичные сервисы; блокировать IP общего назначения (CDN, облака); менять пароль пользователя с этого хоста.

### 5.3. Ветки сдерживания (черновик)
> **8.1. Хост онлайн, есть EDR.** L2 изолирует хост в EDR. Сразу после — звонок пользователю: «Компьютер временно отключён от сети по требованию ИБ. Не выключайте и не перезагружайте его. Не вводите пароли. Вам перезвонят из ИТ».
> **8.2. Хост VIP / критичный бизнес-процесс.** L2 звонит IM; IM согласует изоляцию с руководителем пользователя / владельцем процесса. Если согласование не получено за 15 минут при признаках P2 — IM принимает решение единолично (по IR-плану решения об изоляции — за IM).
> **8.3. Хост офлайн или без EDR.** Заблокировать учётку и отозвать сессии (раздел 9); заблокировать IOC на NGFW; если хост в VPN — отключить VPN-сессию; позвонить пользователю: «отключите Wi-Fi/кабель, не выключайте ноутбук, принесите в ИТ». Поставить в EDR задачу на изоляцию при выходе на связь (если продукт поддерживает [проверить]).
> **8.4. Признаки целевой атаки** (ручная разведка, фреймворк C2, движение к серверам). Не блокировать по одному IOC. IM собирает L2 + ИТ и планирует одномоментное сдерживание всех затронутых хостов и учёток. Параллельно — оценка P1 и PB-02.

### 5.4. Учётные данные и сессии (черновик)
> Применяется, если запуск подтверждён и не исключено, что вредонос — стилер, RAT или загрузчик.
> 1. **После изоляции** ИТ по заявке L2 с чистого устройства: отзывает все сессии и токены пользователя в облачной почте, SSO, VPN; меняет доменный пароль; проверяет и при необходимости перерегистрирует методы MFA.
> 2. L2 проверяет облачную почту: правила пересылки и перемещения, делегирование доступа, подключённые приложения, входы за 14 дней (IP, страна, устройство).
> 3. L2 составляет список сервисов из хранилищ паролей браузеров на хосте (по названиям сайтов, без извлечения самих паролей — [проверить, допустимо ли это по внутренним правилам]) и передаёт владельцам систем: админка сайта, API, 1С, банк-клиент, сторонние SaaS.
> 4. Если на хосте работали привилегированные учётки (вход 2/10/11 за 14 дней) — их пароли тоже меняются, IM оценивает компрометацию AD.
> 5. Если хост бухгалтерии с банк-клиентом — бухгалтерия немедленно связывается с банком для приостановки исходящих платежей и перевыпуска ключей/токенов (по процедуре банка).
> 6. Пользователю — проинформировать о смене паролей и личных аккаунтов, если в браузере были сохранены личные пароли.

### 5.5. Сбор улик (черновик)
> L2 собирает в порядке: (1) дамп памяти; (2) процессы, соединения, DNS-кэш; (3) автозапуск (autorunsc); (4) триаж-пакет KAPE/Velociraptor; (5) образец файла из карантина/EDR.
> Каждый файл улики хешируется (SHA256), хеш вписывается в тикет. Хранение — в выделенном хранилище ИБ с ограниченным доступом. Образцы — только в архиве с паролем `infected`. В тикете — кто собрал, когда, каким инструментом, где лежит.
> Дамп памяти обязателен при P2+ и при P3, если вредоносный процесс ещё работает или есть признаки бесфайлового выполнения.

### 5.6. Коммуникации (черновик таблицы)

| Условие | Кого | Когда | Кто сообщает | Канал |
| --- | --- | --- | --- | --- |
| P3 | дежурный L2 | сразу после триажа | L1 | тикет + звонок ночью |
| P2 | IM | ≤ 15 мин после присвоения | L2 | звонок |
| P1 | IM, директор, юрист | ≤ 15 мин | IM | звонок, резервный канал |
| Изоляция хоста | пользователь, его руководитель | сразу после изоляции | L2 / ИТ | телефон |
| Переустановка | ИТ | при решении | L2 | тикет |
| Подозрение на доступ к ПДн | юрист/DPO | сразу | IM | звонок |
| Украдены доступы к системе | владелец системы | сразу после выявления | IM | звонок |
| Банк-клиент | бухгалтерия, банк | немедленно | IM / главбух | телефон |
| > 3 хостов одного письма/вложения | IM, затем сотрудники через IM/PR | по решению IM | IM / PR | рассылка без деталей |

Шаблон звонка пользователю:
> «Здравствуйте, это служба ИБ. На вашем компьютере сработала защита. Мы временно отключили его от сети. Пожалуйста, не выключайте и не перезагружайте его, не вводите на нём пароли и не пересылайте никому файлы. Подскажите: что вы открывали или устанавливали сегодня около <время>? Не вставляли ли команды из браузера в окно "Выполнить"? С вами свяжется ИТ по поводу подменного устройства».

### 5.7. Разведданные и проверка IOC (черновик)
> Хеш, домен, IP проверять в TI-сервисах **только как индикаторы**, без загрузки файла. Если TI ничего не знает — это не повод закрыть. Файл — во внутреннюю песочницу (почтовая песочница) с разрешения L2. Результат TI в тикете: источник, вердикт, семейство, дата первого обнаружения.

### 5.8. Критерии закрытия (черновик чек-листа)
> - [ ] Вектор проникновения установлен (письмо / сайт / USB / ПО / неизвестно — с обоснованием и согласием IM).
> - [ ] Скоупинг по файлу, сети, почте, пользователю, хосту и поведению выполнен; запросы и результаты в тикете.
> - [ ] Других заражённых хостов нет или они обработаны отдельными тикетами.
> - [ ] Сессии отозваны, пароли сменены, MFA проверена; список сторонних сервисов передан владельцам.
> - [ ] Хост переустановлен (или очищен по критериям 3.7), агенты EDR/АВ работают, исключений АВ нет.
> - [ ] Изоляция снята с апрувом L2.
> - [ ] IOC в блок-листах; правила SIEM на IOC на 14 дней.
> - [ ] Вопрос ПДн закрыт решением юриста/DPO (если открывался).
> - [ ] Для P1/P2 — назначен разбор; для P3 — краткий вывод «что улучшить в детекте».

### 5.9. Разбор и улучшения (черновик)
> По каждому подтверждённому случаю L2 отвечает: на каком шаге цепочки нас могли остановить раньше (почтовый шлюз, NGFW-категория, блок макросов, запрет запуска из `%AppData%`, обучение)? Какой детект сработал поздно или не сработал? Создать задачу на правило/исключение с ответственным и сроком.

### 5.10. Схема решений (текстовая, для приложения)
```
Сработка АВ/EDR/NGFW
  └─ Агент онлайн? ── нет ─→ Ветка 8.3 (офлайн)
       └─ да
  └─ FP? (подпись, известное ПО, заявка ИТ) ── да ─→ Закрыть с обоснованием, исключение через L2
       └─ нет / неясно
  └─ Был запуск? ── нет ─→ P4: проверить источник, скоупинг по хешу/письму, закрыть
       └─ да
  └─ Есть C2 / кража учётных / HackTool / отключение защиты / VIP? ── нет ─→ P3
       └─ да ─→ P2
  └─ Админ домена / ПДн / предвестник шифровальщика / >N хостов? ── да ─→ P1, IM + директор + юрист, PB-02/PB-05
  P3+: L2 → изоляция → сбор улик → учётные данные и сессии → скоупинг → переустановка → наблюдение → закрытие
```

## 6. Оценки

| Критерий | Оценка | Обоснование |
| --- | --- | --- |
| Релевантность | **5/10** | Каркас и ключевые принципы верны (АВ удалил ≠ конец, изоляция через EDR, переустановка при сомнении). Но модель угроз отстаёт: пример с макросом Word, нет стилеров, ClickFix, RMM, кражи сессий; «сбросить пароли» не соответствует современной практике; нет ветки P1 и связи с 152-ФЗ. |
| Полнота | **3/10** | Есть скелет фаз. Нет: предусловий, RACI, таймингов, критериев FP, ветки офлайн-хоста, работы с учётными данными и сессиями, скоупинга по пользователю/почте/поведению, правил обращения с уликами, коммуникаций кроме IM, восстановления данных, разбора. |
| Детализация | **2/10** | Ни одного Event ID, поля, запроса, команды, порога, срока. В 3 часа ночи L1 по документу не сможет обосновать вердикт и критичность, L2 не получит пошагового порядка сбора и сдерживания. |

**Можно ли работать по плейбуку ночью на смене:** как напоминание опытному аналитику — да. Как инструкция для L1 — нет: нет критериев, нет полей тикета, нет запросов, нет порядка эскалации и запретов.

## 7. Что я пометил как неуверенное
- Номер подтехники ATT&CK для ClickFix (T1204.004) — проверить по актуальной версии ATT&CK.
- Event ID Windows и Sysmon приведены по памяти; доступность зависит от политики аудита «Альфа-Трейд».
- Поведение облачной почты при смене пароля (отзываются ли токены автоматически) зависит от провайдера.
- Статус `wmic` в актуальных сборках Windows 11.
- Флаги `autorunsc` — сверить с `autorunsc -?`.
- Возможность EDR ставить отложенную изоляцию для офлайн-хоста зависит от продукта.
- Наличие событий чтения файлов профиля браузера в телеметрии EDR зависит от продукта.
- Синтаксис запросов приведён для KQL/SPL; для MaxPatrol SIEM, KUMA и других российских SIEM его нужно переписать, я его не привожу, чтобы не выдумывать.
- Все тайминги из раздела 3.8 и стартовые уровни критичности из 3.1 — учебные.

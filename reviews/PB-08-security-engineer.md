**Предмет ревью:** `/mnt/project-files/ir-study/drafts/PB-08-web-app-breach.md` («PB-08 Взлом веб-приложения»).

**Условные обозначения:** пометка **[проверить]** стоит там, где я не уверен в точной формулировке, номере статьи, сроке или актуальности инструмента. ## Краткий вывод

Для конспекта PB-08 годится: сценарий выбран правильно, техники ATT&CK указаны верно, «типичная ошибка» (ограничиться правилом WAF) действительно самая частая. Как рабочий документ для дежурной смены он не годится. У него три системные проблемы:

1. **Порядок действий опасен для расследования.** Удалить веб-шелл и заблокировать IP раньше, чем определён масштаб, — классическая ошибка: атакующий узнаёт, что его нашли, и переключается на запасные точки закрепления, а у команды пропадают летучие улики.
2. **Сценарий сведён к схеме «PHP-веб-шелл плюс SQLi».** В 2025–2026 годах значительная доля реальных утечек из интернет-магазинов идёт через API (BOLA/IDOR), скомпрометированную админку, внедрённый JavaScript (веб-скимминг), уязвимые плагины CMS, обход WAF напрямую на origin и in-memory веб-шеллы, которые не оставляют файлов. Ни для одного из этих путей у плейбука нет ни триггера, ни действия.
3. **Нет «мяса»:** не сказано, какие журналы и поля смотреть, какие запросы запускать, какие команды выполнять, кто принимает решения, в какие сроки и по каким критериям. В IR-плане есть таблица полномочий и сроков, но плейбук на неё не опирается.

Оценки (подробности в разделе 6): **релевантность 6/10, полнота 3/10, детализация 2/10.**

## 1. Релевантность: соответствие реальной практике SOC/IR 2025–2026

### 1.1. Что сделано верно

- **T1190 и T1505.003** указаны корректно: это базовая пара техник для такого сценария.
- **Граница с PB-S1** проведена правильно: отбитая попытка уходит в плейбук по сработкам WAF, успешная — в PB-08.
- **Повышение до P1 при веб-шелле или доступе к базе клиентов** соответствует IR-плану (утечка ПД = P1).
- **Триггер «процесс веб-сервера запускает командную строку»** — самый надёжный индикатор RCE в современной практике. Правило «web server spawning shell» есть во всех зрелых наборах детектов, включая Sigma.
- **Пересборка из чистой сборки** вместо «лечения» сервера — правильный подход.
- **Смена секретов** упомянута. Её часто забывают.
- **Критерий закрытия «исправлено в коде, а не только правилом WAF»** верен.

### 1.2. Что устарело, неточно или не отражает текущую практику

| № | Утверждение или пробел в плейбуке | Почему это проблема в 2025–2026 | Как правильно |
| --- | --- | --- | --- |
| R1 | Триггер «WAF пропустил запрос, приложение ответило 200 с большим телом» | Сильно утрированный критерий. Blind/time-based SQLi выгружает данные множеством маленьких ответов. При сжатии gzip/br размер в журнале зависит от сжатия. Выгрузка через API (BOLA) выглядит как тысячи легитимных ответов 200 нормального размера. Out-of-band эксфильтрация (DNS, HTTP-запрос с сервера наружу) вообще не отражается в размере ответа. | Несколько независимых признаков: аномальный объём **суммарно** по источнику, токену или сессии; число уникальных идентификаторов объектов на один токен; время ответа (time-based); исходящие DNS- и HTTP-запросы с веб-сервера и сервера БД. |
| R2 | Триггер «новые файлы .php/.jsp в каталоге сайта» | Актуален, но этого мало. Современные веб-шеллы часто: (а) внедряются **в существующий** легитимный файл (index.php, шаблон, плагин); (б) живут только в памяти (Java memory shell: зарегистрированный Filter/Servlet/Valve в Tomcat, Spring Interceptor; .NET-модули в памяти w3wp); (в) маскируются под картинку (.jpg с PHP-кодом, который подключается через LFI) или под `.htaccess`/`.user.ini` с `auto_prepend_file`. | Контроль целостности (FIM) всего webroot и конфигураций против эталона из репозитория. Поиск изменённых, а не только новых файлов. Детект по поведению процесса (EDR). Для Java/.NET отдельная проверка памяти. |
| R3 | Не упомянуты API и мобильное приложение | По архитектуре «Альфа-Трейд» API для мобильного приложения стоит в DMZ. OWASP API Security Top 10 (2023) ставит BOLA на первое место. Перебор `/api/orders/{id}` — один из самых частых путей массовой утечки ПД у ритейла, и проходит он без всякого веб-шелла. | Отдельный подсценарий «Злоупотребление API» с детектами по числу уникальных ID на токен и пресечением через отзыв токенов и rate limit. |
| R4 | Не упомянута компрометация админки CMS (T1078 Valid Accounts) | Вход в админку по украденному или подобранному паролю — частый путь к «взлому сайта»: подмена реквизитов оплаты, выгрузка заказов штатным экспортом, загрузка плагина-бэкдора. WAF в этом случае ничего не видит, потому что запросы легитимны. | Подсценарий «Скомпрометирована админка». Проверка журналов входа в админку, аудита действий администраторов, новых учёток и ролей. |
| R5 | Не упомянут веб-скимминг (внедрение JS на страницу оформления заказа, «Magecart»-подобные атаки) | Для интернет-магазина это профильная угроза: похищаются платёжные данные и ПД прямо в браузере клиента. На сервере нет ни выгрузки, ни сработки WAF. Защита: CSP, SRI, мониторинг изменений клиентских скриптов. | Подсценарий «Внедрение на клиентской стороне». Сверка JS-ресурсов страниц оплаты с эталоном; CSP report-uri как источник сработок. |
| R6 | Нет цепочки поставок (T1195.002, скомпрометированные npm/composer-пакеты, сторонние JS-виджеты, подрядчик-разработчик) | Пересборка «из чистой сборки» не поможет, если заражены сам репозиторий, CI/CD или зависимость. | Проверка целостности репозитория, конвейера CI/CD и lock-файлов. Сборка с зафиксированными версиями и проверкой хешей. |
| R7 | Нет обхода WAF через прямое обращение к origin | Частая находка в 2025–2026: IP сервера-источника известен (DNS-история, сертификаты, поддомены), и атакующий ходит напрямую, мимо WAF/CDN. Тогда журналы WAF «чистые», и аналитик делает ложный вывод, что атаки не было. | Проверка по NGFW: были ли входящие соединения на 80/443 веб-сервера не с адресов WAF/балансировщика. Закрытие origin для всех, кроме WAF. |
| R8 | Не учтены контейнеры и оркестрация | Если сайт крутится в Docker/Kubernetes, «образ диска сервера» неприменим в лоб: контейнер эфемерен, перезапуск пода уничтожает улики, а атакующий может выйти на узел или в кластер (сервисный токен, T1552.007 Container API **[проверить номер подтехники]**). | Отдельная ветка сбора улик: `docker diff`, экспорт файловой системы контейнера, снимок узла, журналы аудита API Kubernetes, ротация сервисных токенов. |
| R9 | Не учтено, что база клиентов стоит в **серверном сегменте**, а сайт — в DMZ | Взлом сайта почти автоматически означает доступ к учётке БД, а возможно, и путь из DMZ во внутреннюю сеть (а если веб-сервер в домене, то и к AD). Плейбук этого перехода не рассматривает. | Обязательная проверка бокового перемещения DMZ → серверный сегмент (журналы NGFW, EDR на сервере БД). Ветвление на плейбук компрометации AD. |
| R10 | «Блокировка IP атакующего» как стандартная мера | В 2025–2026 годах атакующие повсеместно используют резидентные прокси, Tor, облачные VPS, ротацию адресов. Блокировка IP почти ничего не даёт против целенаправленной атаки, зато сообщает атакующему, что его заметили. | Блокировка IP — тактическая мера против автоматического сканирования, применять после определения масштаба. Основные меры: виртуальный патч на класс атаки, закрытие точки входа, отзыв учёток и токенов. |
| R11 | Типы атак: «SQLi, RCE, загрузка файлов» | Перечень неполный. Не хватает SSRF (особенно к метаданным облака, T1552.005), десериализации, SSTI, LFI/Path Traversal с чтением конфигов (`.env`, `wp-config.php`, `bitrix/.settings.php`), XXE, обхода аутентификации, IDOR/BOLA, mass assignment. | Использовать классификацию OWASP Top 10 (редакция 2021; в конце 2025 года вышла редакция 2025 **[проверить статус и состав]**) плюс OWASP API Security Top 10 2023. |
| R12 | Нет специфики российского e-commerce | В РФ значительная часть интернет-магазинов работает на 1С-Битрикс с интеграцией с 1С. Исторически у Битрикс были критичные RCE в модулях (например, в модуле «Опросы, голосования», CVE-2022-27228 **[проверить]**), а также атаки через устаревшие версии и сторонние модули Marketplace. | Добавить раздел «Стек сайта», чтобы плейбук знал свою платформу: пути к журналам, конфигам с секретами, журналу событий CMS. |

**Итог по релевантности:** базовая модель угрозы корректна, но устарела примерно на 5–7 лет. Это сценарий «PHP-сайт на одном сервере, атакуют через SQLi и заливку шелла». Для ритейла 2025–2026 годов не хватает API, админки, клиентской стороны, цепочки поставок, контейнеров и обхода WAF.

### 2.2. Подготовка (специфичная для сценария)

Пропущено полностью. Должно быть:

- Инвентаризация: все публичные веб-приложения, поддомены, API, тестовые и staging-стенды (часто наименее защищены и содержат копию боевой БД с реальными ПД), владельцы, стек, версии, подрядчики.
- Эталон: хеши релиза или git-тег текущей версии на проде, чтобы можно было сравнить файлы.
- Журналирование: формат access-журналов с реальным IP клиента (X-Forwarded-For / X-Real-IP), временем ответа, размером, User-Agent, ID запроса (сквозной `X-Request-ID` от WAF до приложения); аудит СУБД (pgaudit, MariaDB server_audit / Percona audit, SQL Server Audit); журнал действий в админке; отправка всего в SIEM в реальном времени (атакующий с правами root чистит локальные журналы — T1070.002).
- EDR (или хотя бы auditd + Sysmon for Linux) на веб-серверах в DMZ и на сервере БД.
- FIM (AIDE, Wazuh syscheck, функциональность EDR) на webroot и конфигурациях.
- Egress-политика на NGFW для DMZ по принципу «запрещено всё, кроме списка» и заранее согласованный перечень обязательных внешних адресов (платёжный шлюз, службы доставки, SMS, почта, обновления).
- Заранее подготовленная страница техработ на уровне WAF/CDN/балансировщика (а не на самом сервере).
- Возможность переключиться на резервный чистый экземпляр (blue/green), инфраструктура как код, «золотой образ».
- Инструменты сбора улик, заранее скопированные в доверенное место: статически собранные утилиты, AVML/LiME, UAC, офлайн-коллектор Velociraptor; для Windows/IIS — WinPMem или аналог, KAPE **[проверить условия лицензии KAPE]**.
- Контакты: хостинг/облако, разработчик (если подрядчик), платёжный провайдер, CDN/anti-DDoS, юрист.
- Матрица секретов: какие секреты лежат на веб-сервере и как их сменить (порядок, кто, сколько времени, влияние на бизнес).

### 2.3. Обнаружение и триаж

Пропущено:

- **Роль L1.** Что делает дежурный L1 в первые 15 минут: принять, проверить базовые признаки, эскалировать на L2 и IM. Сейчас триаж начинается сразу с L2.
- **Критерии «атака успешна»** (отличие от PB-S1).
- **Определение подсценария** и выбор ветки.
- **Вопрос «атака идёт сейчас?»** От него зависит стратегия сдерживания.
- **Немедленное сохранение журналов** вне сервера (до любых действий на сервере).
- **Ретроспектива:** сработка может отражать не начальное проникновение, а действия после него. Веб-шелл мог появиться за недели или месяцы до этого. Нужен поиск назад во времени на всю глубину хранения.
- **Источники данных** с названиями журналов и полей (см. раздел 3).
- **Проверка других серверов фермы и других приложений** на ту же уязвимость и те же IOC.
- **Проверка, не наш ли это пентест или bug bounty.** Есть в PB-S1, в PB-08 нет.
- **Проверка threat intelligence:** известная CVE, активная эксплуатация (каталог CISA KEV, бюллетени НКЦКИ/ФСТЭК БДУ **[проверить, в каком виде НКЦКИ публикует бюллетени]**).

### 2.4. Анализ и определение масштаба

Пропущено:

- Хронология от первого запроса разведки (T1595) до текущего момента.
- Полный перечень веб-шеллов и механизмов закрепления: cron (T1053.003), systemd (T1543.002), `authorized_keys` (T1098.004), новые пользователи (T1136.001), `ld.so.preload`, PAM-модули, изменённые бинарники, плагины CMS, задания в админке, триггеры и хранимые процедуры в БД.
- Учётные данные, к которым атакующий имел доступ (T1552.001: `.env`, конфиги, история shell, переменные окружения процессов).
- Боковое перемещение из DMZ (T1021, T1210), туннели (T1572: chisel, frp, ngrok, SSH-туннели), прокси (T1090).
- Действия с данными: чтение (T1005/T1213), упаковка (T1560), выгрузка (T1041/T1567), изменение (T1565.001 — цены, реквизиты оплаты, промокоды, внедрённый JS).
- Побочные цели: майнер (T1496), рассылка спама, размещение фишинговых страниц на домене компании, SEO-спам. Это тоже инциденты, и они влияют на репутацию домена.
- Объём и состав затронутых ПД — ввод для PB-05 и юриста.

### 2.5. Решения и ветвления

В текущем плейбуке нет ни одной явной точки принятия решения. Нужны как минимум:

1. Атака успешна? (нет → PB-S1, P4/P3)
2. Какой подсценарий? (ветки A–G)
3. Есть ли выполнение кода на сервере? (да → P1, сервер считается полностью скомпрометированным)
4. Затронуты ли ПД? (да или нельзя исключить → P1, параллельный запуск PB-05, сразу юрист)
5. Атакующий активен сейчас и идёт ли выгрузка? (стратегия: немедленное сдерживание или скрытное наблюдение с ограниченным окном)
6. Есть ли признаки выхода за пределы DMZ? (да → плейбук компрометации AD/сервера, расширение масштаба)
7. Нужна ли остановка сайта? (матрица «ущерб от простоя против ущерба от продолжения атаки», апрув IM + владелец, при полной остановке — директор)
8. Пересобрать или лечить на месте? (при RCE — только пересборка)
9. Из какой точки восстанавливать данные? (бэкап до компрометации или очистка текущей БД)
10. Подавать заявление в правоохранительные органы? (решает руководство с юристом)

### 2.6. Сдерживание

Пропущено:

- Стратегия «сначала определить масштаб, потом действовать одновременно» и исключение из неё (активная выгрузка ПД).
- Меры с минимальным влиянием на бизнес: отключение конкретной функции или модуля, закрытие админки по списку IP/VPN, перевод группы правил WAF из detect в block, rate limit на API, отзыв токенов и сессий.
- Изоляция сервера: в EDR, через NGFW, переключение балансировщика на чистый экземпляр.
- Ограничение доступа веб-сервера к БД (временно урезать права учётки БД, запретить FILE/`COPY ... TO PROGRAM`/`xp_cmdshell`).
- Закрытие прямого доступа к origin мимо WAF.
- Порядок смены секретов (сначала отрезать доступ, потом менять, иначе атакующий прочитает новые).
- Кто какое действие выполняет и чей нужен апрув (по правилу полномочий IR-плана: остановка сервера или сайта — только IM + владелец системы).

### 2.7. Сбор улик (форензика)

Пропущено:

- Порядок по летучести (RFC 3227): память → процессы и сеть → временные файлы → диск → журналы на удалённых системах.
- Правила: не перезагружать, не запускать антивирусное «лечение» до снятия копии, не открывать веб-шелл в браузере, не запускать на сервере недоверенные бинарники.
- Хеширование (SHA-256), фиксация времени и исполнителя, цепочка хранения (chain of custody).
- Сохранение метаданных файлов: mtime, ctime, atime, birth time, владелец, inode.
- Улики из облака или виртуализации: снимок диска и, если гипервизор позволяет, памяти ВМ.
- Улики на стороне WAF, CDN, балансировщика, платёжного провайдера.

### 2.8. Устранение и восстановление

Пропущено:

- Определение корневой причины, включая ответ на вопрос «почему WAF пропустил» (режим detect, неразобранное JSON/multipart-тело, лимит инспекции тела, кодировка, обход через origin).
- Полная матрица смены секретов, включая неочевидные: ключ подписи сессий/JWT (`APP_KEY` в Laravel, `secret_key_base` в Rails, `machineKey` в ASP.NET — его кража даёт RCE через ViewState), ключи платёжного шлюза, приватный ключ TLS (перевыпуск и отзыв сертификата), SSH-ключи деплоя, токены CI/CD, ключи S3/облака, SMTP, ключи интеграции с 1С.
- Очистка БД: вредоносные учётки в админке, внедрённый JS в контенте, шаблонах и настройках, изменённые реквизиты оплаты и цены.

Пропущено:

### 3.3. «Триаж, шаг 1: по журналам WAF и веб-сервера найти уязвимый URL и тип атаки»

**Проблема:** не сказано, где журналы, какие поля, как связать WAF и веб-сервер, за какой период искать.

**Нужно расписать:**

- **Журналы и пути** (под стек «Альфа-Трейд», заполнить при подготовке):
  - WAF: журнал событий безопасности + журнал всех запросов (если ведётся); поля: время, client IP, X-Forwarded-For, метод, URI, параметры, тело (если сохраняется), решение (block/detect/pass), ID правила, ID запроса.
  - Nginx: `/var/log/nginx/access.log*`, `error.log*`; рекомендуемый формат: `$time_iso8601 $remote_addr $http_x_forwarded_for $request_method $request_uri $status $body_bytes_sent $request_time $upstream_response_time "$http_user_agent" "$http_referer" $request_id`.
  - Apache: `/var/log/apache2/` или `/var/log/httpd/`.
  - PHP-FPM: журнал пула, slowlog (полезен: показывает стек вызовов долгих запросов).
  - IIS: `%SystemDrive%\inetpub\logs\LogFiles\W3SVC<ID>\`, поля `cs-uri-stem`, `cs-uri-query`, `sc-status`, `sc-bytes`, `time-taken`, `c-ip` (за прокси — настроить custom field с X-Forwarded-For).
  - Tomcat: `localhost_access_log*`, `catalina.out`.
  - Журнал приложения/CMS (для Битрикс — журнал событий модуля «Проактивная защита» и событийный журнал в БД **[проверить точные названия]**).
- **Учёт времени:** WAF обычно пишет в UTC, веб-сервер — в локальное время. В тикете фиксировать всё в одном часовом поясе (IR-план использует UTC+3).
- **Связка запросов:** по `request_id`, если он есть, иначе по совокупности времени, IP, URI и User-Agent.
- **Период:** не «сутки», как в PB-S1, а от текущего момента назад на всю глубину хранения (90 дней по IR-плану), с отдельным поиском первого появления IOC.
- **Примеры запросов:**

```
# Все запросы с IP атакующего, включая неблокированные, с сортировкой по времени
index=waf OR index=web src_ip IN (<IOC_IP>) earliest=-90d
| table _time src_ip xff method uri status bytes request_time user_agent waf_action rule_id
| sort _time

# Успешные ответы на запросы, которые WAF только пометил (detect), а не заблокировал
index=waf waf_action IN ("detect","log","pass") attack_class IN ("sqli","rce","lfi","upload","ssrf","deser")
| join request_id [ search index=web status<400 ]
| stats count values(uri) by src_ip attack_class

# Редкие POST-цели (кандидаты в веб-шеллы)
index=web method=POST status=200 earliest=-30d
| stats dc(src_ip) as ips count values(src_ip) by uri_path
| where ips<=2
| sort - count

# Сканеры по User-Agent (вспомогательный признак: UA подделывается)
index=web user_agent IN ("*sqlmap*","*nuclei*","*ffuf*","*gobuster*","*dirsearch*","*nikto*","*python-requests*","*Go-http-client*","*curl*")
| stats count min(_time) max(_time) by src_ip user_agent
```

- Быстрый ручной разбор на копии журнала (не на продуктивном сервере):

```bash
# Редкие URI, к которым шли POST-ом с ответом 200 (комбинированный формат журнала)
awk '$6=="\"POST" && $9==200 {print $7}' access.log | sort | uniq -c | sort -n | head -50
# Все действия одного IP
grep -F '203.0.113.45' access.log* | sort -k4,4
# Признаки SQLi/LFI/RCE в URI
grep -Ei "union(.|%20|\+)+select|information_schema|sleep\(|benchmark\(|pg_sleep|\.\./|%2e%2e|/etc/passwd|php://|data://|expect://|\$\{jndi:|cmd=|exec=" access.log*
```

### 3.5. «Триаж, шаг 3: проверить, что ушло из базы (размеры ответов, журналы СУБД)»

**Проблема:** журналы СУБД по умолчанию почти всегда выключены или пишут только ошибки. Если аудит не включён заранее, этот шаг невыполним, и плейбук должен это признать и дать обходные пути.

**Нужно:**

- **Источники:**
  - PostgreSQL: pgaudit или `log_statement`, `log_min_duration_statement`; `pg_stat_statements` (агрегированная статистика запросов: даже без аудита видно аномальные запросы и число возвращённых строк, поле `rows`).
  - MySQL/MariaDB: general log (дорого, обычно выключен), slow log, MariaDB Audit Plugin, Percona Audit Log, `performance_schema.events_statements_history_long`.
  - MS SQL: SQL Server Audit, Extended Events, `sys.dm_exec_query_stats`.
  - Журнал приложения/ORM, если пишет запросы.
  - Сетевой уровень: объём трафика между веб-сервером и БД (NGFW/NetFlow) за период атаки в сравнении с обычным.
- **Признаки** в запросах: `UNION SELECT`, обращения к `information_schema`/`pg_catalog`/`sys.*`, `SLEEP()`/`pg_sleep()`/`BENCHMARK()`/`WAITFOR DELAY`, `INTO OUTFILE`/`LOAD_FILE()`, `COPY ... TO PROGRAM` (PostgreSQL), `xp_cmdshell` (MS SQL), `SELECT *` без `LIMIT` по таблицам клиентов, запросы от учётки веб-приложения к таблицам, которые приложение обычно не читает.

### 3.6. «Сдерживание, шаг 1: виртуальный патч на WAF, блокировка IP атакующего»

**Нужно:**

- **Правило, а не «блок именно этой атаки»:** виртуальный патч должен закрывать **класс** уязвимости на этом эндпоинте (например, разрешить в параметре `id` только `^\d{1,10}$`, запретить загрузку файлов с расширениями, отличными от разрешённого списка, и проверять сигнатуру содержимого), а не конкретную строку эксплойта, которую атакующий легко изменит.
- **Проверка, что правило в режиме block** (ловушка из PB-S1), и что WAF разбирает формат тела (JSON, XML, multipart, GraphQL), и что тело не превышает лимит инспекции.
- **Тест:** повторить запрос с полезной нагрузкой из журнала (из внутреннего сегмента, с согласия IM, на стенде или с безопасной полезной нагрузкой) и убедиться, что WAF блокирует.
- **Блокировка IP:** только после того, как определён масштаб, или сразу, если идёт активная выгрузка. Срок, обоснование и ссылку на тикет записывать в комментарий правила.
- **Кто и апрув:** L2 сам (по правилу полномочий IR-плана: блокировка внешнего IP — в полномочиях L2; виртуальный патч на один URL — тоже, если не ломает бизнес-функцию; иначе — IM + владелец).

### 3.7. «Сдерживание, шаг 2: удалить веб-шелл (сохранив копию); страница техработ»

Этот шаг детализирован хуже всего и потенциально вреден (см. раздел 4). **Нужно:**

- Удаление веб-шелла перенести из сдерживания в устранение, кроме случая активного ущерба.
- Как делать копию: `cp --preserve=all` или `tar --xattrs --acls -cpf` с записью вывода `stat` (включая ctime и birth time) **до** копирования, SHA-256 исходника и копии, запись в журнал улик.
- Страница техработ: включается на WAF/CDN/балансировщике, а не заменой файлов на скомпрометированном сервере.
- Апрув: IM + владелец сайта (по IR-плану). Ориентир для решения: условная стоимость простоя 1 млн ₽/ч против риска продолжения выгрузки ПД (штрафы, ущерб, уведомление тысяч клиентов). Решение и время записываются в тикет.

### 3.8. «Артефакты: журналы WAF и веб-сервера, копия веб-шелла, образ диска сервера, журналы СУБД»

**Нужно:** порядок, инструменты, контроль целостности.

| Порядок | Что | Как (Linux) | Как (Windows/IIS) | Кто |
| --- | --- | --- | --- | --- |
| 0 | Журналы вне сервера | Убедиться, что SIEM получил их; экспорт WAF/CDN/балансировщика/NGFW за 90 дней; временно отключить удаление по ротации (logrotate) или скопировать архивы | То же, плюс выгрузка EVTX | L1/L2 |
| 1 | Память | AVML (статический бинарник) или LiME (нужен модуль под конкретное ядро); анализ — Volatility 3 (нужна таблица символов ISF под ядро) | WinPMem, DumpIt, Magnet RAM Capture **[проверить актуальность]** | L2 |
| 2 | Процессы, сеть, открытые файлы | `ps -eo pid,ppid,user,lstart,cmd --forest`, `ss -tanpu`, `lsof -nP`, `ls -l /proc/*/exe 2>/dev/null \| grep deleted`, `cat /proc/<pid>/environ`, `cat /proc/<pid>/cmdline`, `ls -l /proc/<pid>/cwd` | `tasklist /v`, `netstat -anob`, Sysinternals (Autoruns, Handle) | L2 |
| 3 | Быстрая триаж-коллекция | UAC (Unix-like Artifacts Collector) или офлайн-коллектор Velociraptor | KAPE или Velociraptor | L2 |
| 4 | Webroot с метаданными | `tar --xattrs --acls -cpf` + SHA-256 | Robocopy с `/COPY:DATSOU`, лучше из теневой копии или снимка | L2/ИТ |
| 5 | Диск | Снимок ВМ/облачного диска или `dd`/`dc3dd`/`ewfacquire` | Снимок ВМ, FTK Imager | ИТ под контролем L2 |
| 6 | Состояние БД | Экспорт журналов аудита, `pg_stat_statements`, список пользователей и прав БД, снимок БД (если допустимо по объёму) | То же | ИТ/DBA |
| 7 | Контейнеры (если есть) | `docker inspect`, `docker diff`, `docker export`, журналы контейнера, снимок узла; в Kubernetes — журналы аудита API-сервера | — | DevOps под контролем L2 |
| 8 | Внешние | Журналы CDN/WAF-провайдера, хостинга, платёжного провайдера | — | IM запрашивает |

Каждая единица улик фиксируется в журнале: что, откуда, когда (UTC+3), кто, чем снято, SHA-256, где хранится. Инструменты запускаются с доверенного носителя или из доверенного каталога, вывод пишется **не** на исследуемый диск (сетевое хранилище, подключённый диск).

### 3.9. «Сдерживание, шаг 3: ограничить исходящие соединения из DMZ на NGFW»

**Нужно:**

- Перечень разрешённых направлений (платёжный шлюз, доставка, SMS, почта, обновления, NTP, DNS) — заранее, в подготовке.
- Порядок: сначала включить журналирование и оценить, какие исходящие соединения есть сейчас (чтобы не сломать оплату), затем запрет всего остального.
- Одновременно: ограничить DMZ → серверный сегмент только портом БД с конкретного сервера и запретить SMB, RDP, SSH, LDAP/Kerberos из DMZ во внутреннюю сеть, если они не нужны.
- DNS: принудительно использовать только внутренний резолвер с журналированием, запретить прямой DNS наружу (иначе остаётся канал OOB-эксфильтрации и туннелирования).
- Апрув: изменение правил NGFW для продуктивного сервиса — IM; если затрагивает оплату или доставку — плюс владелец.

### 3.10. «Устранение и восстановление»

**Нужно:** чек-лист устранения и отдельный чек-лист восстановления с критериями (см. раздел 5.8–5.9).

### 3.11. «Уведомить: IM, владелец сайта, разработчики. При доступе к данным клиентов дальше PB-05»

**Нужно:** матрица уведомлений с триггером, сроком, ответственным и каналом (см. 5.10). Отдельно указать, что юрист подключается параллельно, а не «дальше».

### 3.12. Тайминги

## 4. Ошибки и риски

| № | Что в плейбуке | Риск | Как исправить |
| --- | --- | --- | --- |
| E1 | «Удалить веб-шелл» на этапе сдерживания | **Атакующий узнаёт о раскрытии** и использует запасные шеллы, туннели, украденные учётки; может перейти к деструктиву (удаление БД, шифрование) или ускорить выгрузку. Типичная картина: один шелл удалили, а у атакующего было ещё пять. | Сначала определение масштаба (все шеллы, закрепление, учётки), затем **одномоментное** сдерживание и устранение по согласованному плану («в час Ч одновременно»). Исключение — активная выгрузка ПД или деструктив: тогда изоляция сразу. |
| E2 | Удаление веб-шелла до снятия памяти | Теряются процессы, сетевые соединения, расшифрованные в памяти полезные нагрузки, ключи; для in-memory шеллов — сам шелл. | Порядок по летучести: память → процессы и сеть → файлы → диск. |
| E3 | «Сохранив копию» без требований к копии | Обычное копирование меняет atime, теряет владельца и временные метки; копия без хеша не годится как доказательство. | `stat` до копирования, копирование с сохранением атрибутов, SHA-256, журнал цепочки хранения. |
| E4 | Нет запрета открывать веб-шелл | Аналитик или администратор «проверяет» шелл, открывая URL в браузере с корпоративного IP: атакующий видит это в своих журналах или через beacon; на сервере появляются новые записи, которые мешают хронологии; в шелле может быть ловушка. | Явный запрет. Анализ шелла — только как файла, в изолированной среде. |
| E5 | Страница техработ без указания, где её включать | Если ИТ подменит index.php на скомпрометированном сервере, это изменение улик и не отрезает атакующего (шелл по другому пути продолжит работать). | Техработы — на WAF/CDN/балансировщике; сервер при этом изолируется отдельно. |
| E6 | Блокировка IP атакующего как первая мера | Ложное чувство защищённости, раскрытие факта обнаружения; при блокировке IP из общих диапазонов (мобильные операторы с CGNAT, облачные прокси) — блокировка клиентов. | Блокировка IP — вспомогательная мера, с ограниченным сроком, после определения масштаба. |
| E7 | Смена секретов без порядка | Если сменить пароль БД, пока атакующий имеет RCE на сервере, он прочитает новый пароль из конфига через минуту. | Сначала отрезать доступ атакующего (изоляция, пересборка на чистом сервере), затем менять секреты, затем разворачивать новые секреты только на чистую инфраструктуру. |
| E8 | «Ограничить исходящие соединения из DMZ» без списка разрешённых направлений | Отключение оплаты, доставки, SMS-уведомлений; простой ~1 млн ₽/ч; хаотичный откат правил под давлением бизнеса. | Заранее согласованный список разрешённых направлений; изменения через IM и владельца. |
| E9 | Триаж ограничен «уязвимым URL» | Сработка может отражать действия после проникновения, а точка входа — недели назад. Если искать только вокруг сработки, исправят не ту уязвимость. | Ретроспективный поиск на всю глубину хранения; поиск первого появления каждого IOC; отдельный вопрос «как сюда попали». |
| E10 | Нет проверки бокового перемещения DMZ → внутренняя сеть | Инцидент «закрыт» пересборкой веб-сервера, а атакующий остался на сервере БД или в AD. | Обязательный шаг определения масштаба: NGFW DMZ → серверный сегмент, EDR на БД, входы учёток веб-сервера во внутренние системы. |
| E11 | Юрист — «дальше PB-05» | Пропуск 24-часового срока: определение масштаба на сервере занимает дни, а срок идёт с момента выявления. | Юрист оповещается сразу, как только доступ к ПД нельзя исключить. |
| E12 | «Развернуть сайт из чистой сборки» без проверки репозитория, CI/CD, зависимостей и БД | Повторное заражение: бэкдор в репозитории/плагине/контенте БД вернётся в «чистую» сборку. Каталог uploads переносится вместе с шеллами. | Проверка репозитория (коммиты за период, авторы, подписи), CI/CD (токены, раннеры), lock-файлов зависимостей; очистка БД; сканирование uploads; запрет исполнения скриптов в каталоге загрузок. |
| E13 | «Удалить веб-шелл» поручено ИТ | Администраторы без подготовки по форензике портят улики, перезапускают сервисы, «заодно чистят» журналы. | Действия на скомпрометированном сервере — только под контролем L2 и по чек-листу. |
| E14 | Нет решения «восстановление БД из бэкапа или очистка» | Откат к бэкапу до компрометации может стереть заказы и платежи за несколько недель; без отката в БД остаются вредоносные изменения. | Сравнение текущей БД с бэкапом до компрометации; точечная очистка; решение — владелец системы с IM. |
| E15 | Нет учёта обхода WAF через origin | Ложный вывод «WAF ничего не видел, значит, атаки не было», а виртуальный патч на WAF ничего не меняет. | Проверка входящих соединений на origin не с адресов WAF; закрытие origin. |
| E16 | Нет действий с сессиями и токенами | После смены паролей атакующий остаётся залогинен в админке по украденной cookie/JWT (T1550.004 **[проверить номер подтехники]**). | Инвалидация всех сессий администраторов, ротация ключа подписи сессий/JWT, отзыв API-токенов. |
| E17 | Нет мер против повторной атаки в окно восстановления | Атакующий, знающий уязвимость, вернётся сразу после открытия сайта, если исправление не доставлено. | Открывать только после подтверждённого исправления (ретест) и при включённом усиленном мониторинге. |
| E18 | Антивирусное «лечение» не упомянуто как запрет | Антивирус или EDR в режиме «удалить» уничтожают образцы до сбора; карантин меняет метаданные. | Перевести реакцию EDR на сервере в «блокировать и сохранить» на время расследования; образцы извлекать из карантина с хешами. |

### 5.1. Паспорт

> Версия: 2.0 · Владелец: руководитель ИБ · Пересмотр: раз в 6 месяцев и после каждого применения · Последние учения: ___
> **Применяется:** подтверждённая или вероятная успешная эксплуатация сайта магазина, API мобильного приложения, админки CMS, а также внедрение кода на страницы сайта.

### 5.3. Дерево решений (текстом)

> **Р1. Атака успешна?** Признаки успеха: ответ приложения содержит данные или результат команды; последующие запросы атакующего используют полученную информацию; EDR видит процессы от веб-сервера; появились или изменились файлы; созданы учётки; есть исходящие соединения с сервера. Нет ни одного признака → вернуть в PB-S1, P4/P3.
> **Р2. Какой подсценарий (A–G)?** Можно несколько. Открыть соответствующие ветки.
> **Р3. Есть выполнение кода на сервере?** Да → P1; сервер считается полностью скомпрометированным (все секреты на нём скомпрометированы, лечение на месте не допускается).
> **Р4. Затронуты ПД или их нельзя исключить?** Да → P1; IM немедленно оповещает юриста; параллельно запускается PB-05; время выявления фиксируется в тикете как отправная точка для 24 ч.
> **Р5. Атакующий активен сейчас?** Признаки: запросы к шеллу за последние 60 минут, активные сессии/соединения, идущая выгрузка.
>  — Идёт выгрузка ПД, деструктив или подмена платёжных реквизитов → **немедленное сдерживание** (изоляция, техработы на WAF), сбор улик параллельно в объёме, который успеваем.
>  — Активности нет или она разведывательная → **сначала определение масштаба** (окно не более 4–6 ч для P1), затем одномоментное сдерживание.
> **Р6. Есть выход за пределы DMZ?** Да → расширить масштаб, привлечь плейбук компрометации AD/серверов, при необходимости — внешнюю DFIR-команду (решение IM, бюджет — директор).
> **Р7. Остановка сайта?** Решают IM и владелец системы; полная остановка бизнеса больше 4 ч или в пиковый период — с директором. Критерий: продолжение работы сайта даёт атакующему доступ к ПД или платежам, и это нельзя закрыть точечной мерой (отключение функции, виртуальный патч, изоляция одного узла).

### 5.4. Первые 60 минут (P1), чек-лист

> 1. [L1, 0–15 мин] Принять сработку, завести тикет, отметить время. Эскалировать L2 и IM звонком. Ничего не делать на сервере.
> 2. [L1/L2, 0–30 мин] Убедиться, что журналы WAF, балансировщика, веб-сервера, приложения, NGFW и EDR за 90 дней есть в SIEM; если нет — выгрузить копию. Запретить удаление журналов ротацией.
> 3. [L2, 0–30 мин] Подтвердить успешность (Р1), определить подсценарий (Р2).
> 4. [IM, ≤45 мин] Присвоить критичность, открыть рабочий канал инцидента (резервный, если могла быть скомпрометирована почта ИТ/разработки), оповестить юриста при Р4 = да, оповестить владельца системы.
> 5. [L2, ≤60 мин] Перевести EDR на сервере в режим «обнаруживать и сохранять, без автоудаления». Начать снятие памяти и летучих данных.
> 6. [IM, ≤60 мин] Принять решение Р5 и записать его в тикет с обоснованием.
> 7. [L2] Не трогать веб-шелл, не открывать его URL, не перезагружать сервер, не перезапускать сервисы.

### 5.5. Анализ и определение масштаба (черновик раздела)

> Цель: до начала устранения ответить на вопросы:
> 1. **Как вошли?** Первая успешная эксплуатация: дата, URI, уязвимость, IP. Почему WAF пропустил: режим detect, нет правила, обход кодировкой, тело не инспектируется, обращение напрямую к origin.
> 2. **Что получили?** Выполнение кода (под каким пользователем: `www-data`, `IIS APPPOOL\…`, root/SYSTEM), чтение файлов (какие), учётки (какие), данные (какие таблицы, сколько строк).
> 3. **Где закрепились?** Все веб-шеллы (новые и изменённые файлы против эталона, in-memory), cron/systemd/authorized_keys/новые пользователи/sudoers/`ld.so.preload`/PAM, модули и агенты CMS, триггеры и процедуры в БД, учётки в админке.
> 4. **Куда пошли дальше?** Соединения из DMZ во внутреннюю сеть (NGFW), входы учёток с веб-сервера (журналы AD: 4624/4625/4768/4769 с IP веб-сервера), туннели (долгие исходящие соединения, нетипичные порты, известные инструменты), другие серверы фермы, staging, API.
> 5. **Что изменили?** Цены, реквизиты оплаты, промокоды, JS на страницах, контент, шаблоны писем.
> 6. **Что вынесли?** Объём и состав данных, канал (HTTP-ответы, OOB, исходящая выгрузка в облако — T1567.002).
> Результат фиксируется в тикете в виде таблицы IOC и хронологии; каждое утверждение помечается «подтверждено» или «предположение».

Полезные проверки на Linux-сервере (выполнять доверенными бинарниками, вывод — на внешний носитель):

```bash
# Закрепление
ls -la /etc/cron* /var/spool/cron/crontabs/ 2>/dev/null; crontab -l -u www-data
systemctl list-unit-files --state=enabled; ls -lt /etc/systemd/system/ /usr/lib/systemd/system/ | head -30
cat /etc/ld.so.preload 2>/dev/null
awk -F: '$3==0 || $3>=1000 {print}' /etc/passwd
find / -xdev -name authorized_keys -exec ls -l {} \; -exec cat {} \; 2>/dev/null
ls -la /tmp /var/tmp /dev/shm
# Пользователь веб-сервера с интерактивной оболочкой или домашним каталогом с историей
grep -E '^(www-data|nginx|apache)' /etc/passwd; ls -la /var/www/.bash_history ~www-data/.* 2>/dev/null
# Входы и аутентификация
last -Faiw; lastb -Faiw | head; journalctl -u ssh --since "-90 days" | grep -E 'Accepted|Failed'
```

```

| stats count values(dest_port) min(_time) max(_time) by dest_ip
| where NOT (dest_ip=<db_server> AND dest_port IN (<db_port>))
```

Запрос на входы в AD с адресов DMZ:


### 5.7. Блок «Чего не делать» (вставить в начало плейбука)

> - Не перезагружать сервер и не перезапускать веб-сервер или пул приложений до снятия памяти.
> - Не удалять веб-шелл до определения масштаба (исключение — активный ущерб, решение IM).
> - Не открывать URL веб-шелла и не «проверять» его работу.
> - Не выполнять `git status`, антивирусное сканирование с лечением и прочие изменяющие операции на живом исследуемом сервере.
> - Не подменять файлы сайта для страницы техработ на скомпрометированном сервере.
> - Не менять секреты, пока атакующий имеет доступ к серверу, на котором они хранятся.
> - Не обсуждать инцидент в каналах, к которым мог получить доступ атакующий (почта и мессенджеры разработчиков, тикеты подрядчика), до проверки.
> - Не вступать в переписку с атакующим (шантаж, требование выкупа) без решения директора и юриста.
> - Не закрывать инцидент на основании одного правила WAF.

### 5.8. Устранение (чек-лист)

> 1. Корневая причина установлена и подтверждена (запрос → уязвимый код/компонент → версия). Если не установлена — это фиксируется, и восстановление идёт с повышенным мониторингом и дополнительными компенсирующими мерами.
> 2. Код исправлен (или компонент обновлён) и прошёл ревью; исправление проверено ретестом на стенде. Проверены аналогичные места в коде (тот же класс уязвимости в других контроллерах).
> 3. Репозиторий проверен: коммиты за период компрометации, авторы, ветки, теги; CI/CD: токены, раннеры, секреты конвейера сменены.
> 4. Зависимости: lock-файлы сверены, сборка воспроизводима, неизвестные пакеты удалены.
> 5. Новый сервер (или контейнеры) собраны с нуля из эталонного образа/IaC; скомпрометированный сервер сохранён как улика и выведен из эксплуатации.
> 6. Каталог загрузок проверен (YARA, расширения, сигнатуры содержимого), исполнение скриптов в нём запрещено конфигурацией веб-сервера.
> 7. БД очищена: лишние администраторы, внедрённый JS/HTML в контенте и настройках, изменённые цены/реквизиты/промокоды, триггеры и хранимые процедуры. Решение «бэкап или очистка» принято владельцем системы и IM.
> 8. Секреты сменены по матрице (5.11) **после** отсечения доступа атакующего.
> 9. Все сессии администраторов и пользователей инвалидированы; ключ подписи сессий/JWT заменён.
> 10. При утечке хешей паролей клиентов — принудительная смена паролей; если алгоритм хеширования слабый (MD5/SHA-1 без соли) — миграция на bcrypt/Argon2 при следующем входе.
> 11. Если атакующий выходил за DMZ — устранение по соответствующему плейбуку завершено.

### 5.9. Восстановление (чек-лист)

> 1. Новый экземпляр подключается за WAF; правила виртуального патча оставлены как дополнительный уровень защиты.
> 2. Origin принимает соединения только от WAF/балансировщика.
> 3. Egress из DMZ — только по списку разрешённых направлений.
> 4. Включены: FIM на webroot, EDR, отправка всех журналов в SIEM, аудит СУБД, правила SIEM на IOC инцидента.
> 5. Внешний скан и ретест уязвимости до открытия.
> 6. Открытие поэтапно (например, сначала каталог и просмотр, затем корзина и оплата), с подтверждением владельца системы.
> 7. Усиленный мониторинг не менее 2 недель (по IR-плану), для P1 рекомендуется 30 дней. Ежедневный просмотр: запросы к старым путям веб-шеллов, соединения на IOC, входы в админку, изменения файлов.
> 8. Мониторинг публикаций (Telegram-каналы, форумы утечек) на предмет базы клиентов — совместно с PB-05.

- **152-ФЗ, ст. 21, ч. 3.1.** Обязанность уведомить РКН о неправомерной или случайной передаче ПД: в течение 24 часов — первичное уведомление (инцидент, предполагаемые причины, предполагаемый вред, принятые меры, контактное лицо), в течение 72 часов — результаты внутреннего расследования и сведения о лицах, действия которых стали причиной (при наличии). Сроки 24/72 ч я помню уверенно; точный перечень сведений — по памяти, **[проверить]**.
- **Ответственность.** В конце 2024 года были приняты поправки в КоАП (ст. 13.11) с существенно повышенными штрафами за утечки ПД, включая оборотные штрафы за повторные нарушения, и отдельная ответственность за неуведомление РКН. Вступили в силу, насколько помню, с 30 мая 2025 года. **[проверить номера частей статьи, размеры и дату вступления в силу]**. Для учебного плейбука достаточно сказать: «неуведомление — отдельное нарушение со штрафом; размеры уточнить у юриста».
- **187-ФЗ** к «Альфа-Трейд» не применим: компания не субъект КИИ (так указано в IR-плане). Если в будущем компания станет субъектом КИИ, нужны отдельные сроки уведомления НКЦКИ; их приводить только по актуальному приказу ФСБ **[проверить]**.
- **«Момент выявления».** Интерпретацию (сработка, подтверждение L2 или решение IM) нужно заранее согласовать с юристом и записать в IR-план. Практичный подход: время, когда IM подтвердил, что доступ к ПД был или не может быть исключён. Это время фиксируется в тикете отдельным полем.

### 5.14. Критерии закрытия (замена текущих)

> Инцидент закрывается, когда выполнены все условия:
> 1. Корневая причина установлена (или зафиксировано, почему не установлена, и приняты компенсирующие меры).
> 2. Уязвимость исправлена в коде/компоненте, ретест пройден; виртуальный патч оставлен как дополнительный уровень защиты.
> 3. Все известные веб-шеллы и механизмы закрепления удалены; сервер пересобран; старый сохранён как улика.
> 4. Проверено отсутствие присутствия атакующего за пределами DMZ.
> 5. Секреты сменены по матрице, сессии инвалидированы.
> 6. БД очищена от вредоносных изменений; владелец подтвердил корректность данных.
> 7. Уведомления отправлены в сроки (РКН, при необходимости — клиенты, платёжный провайдер), копии приложены к тикету.
> 8. Период усиленного мониторинга завершён без повторных признаков.
> 9. Отчёт по шаблону IR-плана подготовлен, улучшения внесены в план работ с ответственными и сроками.

### 5.15. Улучшения защиты после инцидента (раздел 13)

> **Приложение:** исправление класса уязвимостей по всему коду; SAST/SCA в CI; DAST перед релизом; регулярное обновление CMS и модулей; отказ от неподдерживаемых модулей; проверка авторизации на уровне объекта в API (защита от BOLA); rate limit; CSP и SRI для страниц оплаты, мониторинг изменений клиентских скриптов.
> **Инфраструктура:** origin доступен только с WAF; WAF в режиме block для критичных групп правил, инспекция JSON/multipart; egress по списку разрешённых направлений; сегментация DMZ → БД только нужным портом; веб-сервер не в домене; учётка БД с минимальными правами (без FILE, SUPERUSER, `xp_cmdshell`); запрет исполнения скриптов в каталогах загрузок; файловая система webroot только для чтения для пользователя веб-сервера (кроме нужных каталогов).
> **Секреты:** хранилище секретов (Vault или аналог), отсутствие секретов в репозитории и файлах webroot, плановая ротация.
> **Доступ:** админка только через VPN + MFA; отдельные учётки администраторов; журнал действий администраторов в SIEM.
> **Обнаружение:** EDR/auditd на веб-серверах и БД; FIM; аудит СУБД; правила SIEM из раздела 3; внешний мониторинг целостности страниц; приманки (honeytokens) — например, фиктивная запись клиента в БД, обращение к которой даёт сработку.
> **Процесс:** инвентаризация внешнего периметра (attack surface management); регулярный пентест; программа bug bounty (в РФ есть платформы, например Standoff 365 Bug Bounty и BI.ZONE Bug Bounty **[проверить актуальность]**); учения по PB-08 раз в полгода; роль «Разработка/DevOps» в IR-плане.

## 6. Оценка

| Критерий | Оценка | Обоснование |
| --- | --- | --- |
| **Релевантность** | **6/10** | Сценарий и базовые техники (T1190, T1505.003) верны, ключевая ошибка «только WAF» отмечена правильно, триггер по дереву процессов современный. Но модель угрозы узкая и устаревшая: нет API/BOLA, компрометации админки, веб-скимминга, цепочки поставок, in-memory шеллов, обхода WAF через origin, контейнеров; нет учёта того, что база клиентов во внутреннем сегменте. Порядок «удалить шелл и заблокировать IP» не соответствует современной практике IR. |
| **Полнота** | **3/10** | Есть каркас фаз, но нет подготовки, ролей L1 и разработки, точек принятия решения, определения масштаба (закрепление, боковое перемещение, ретроспектива), порядка сбора улик, работы с БД, матрицы секретов, коммуникаций с внешними сторонами и клиентами, регуляторных сроков, наблюдения после восстановления, улучшений защиты. |
| **Детализация** | **2/10** | Каждый шаг описан одной фразой, без журналов, полей, запросов, команд, критериев, сроков и апрувов. Дежурный аналитик не сможет выполнить плейбук без собственной экспертизы; администратор, следующий ему буквально, с высокой вероятностью уничтожит улики. |

**Общий вывод:** PB-08 стоит переписать с нуля по структуре из раздела 5, сохранив из текущей версии границу с PB-S1, ATT&CK-якоря и «типичную ошибку». Приоритет правок: (1) порядок действий и блок «чего не делать», (2) дерево решений и сроки, (3) подсценарии API/админка/скимминг, (4) сбор улик, (5) матрица секретов и уведомлений.
